# Repository audit (2026-09-28)

## Scope and method

Reviewed the whole tracked tree on branch `dev` (201 tracked files) with the
focus on the «Пообъектный план» (renovation plan) vertical: its data model,
read/write path, export pipeline, collaboration layer and the Next.js
workspace that renders it. Secondary passes covered authentication, rate
limiting, the seed/provisioning scripts, CI/Docker/Compose, documentation
drift and test coverage.

Method: read-only inspection (`git status`, `git log`, `git check-ignore`,
file reads) plus targeted searches. No file, schema or configuration was
modified by this audit. Backend tests were **not** executed during the audit
(the suite needs a live Postgres and optionally Valkey), so every finding is
tagged **confirmed** (verified from source/CLI output here) or **needs-run**
(reasoned but not reproduced on this machine).

Line numbers are as of the audit date and will drift; treat them as pointers,
not contracts.

The renovation-plan findings are the ones that matter most, because the plan
is the largest object in the system: 216 typed columns per row (`col_003`
… `col_218`, plus the synthetic asset column `col_002`), a seed approaching
300 000 rows, and a large set of derived/formula columns.

## P0 findings

### AUD-01 — `includeNulls` filter breaks on non-text columns (the 500)

**Evidence** — `back/src/renovation/service.py:561-565`:

```python
if column_filter.includeNulls:
    # An empty string is the same bucket as NULL (the facet collapses
    # both), so keep both here.
    value_conditions.append(raw.is_(None) | (raw == ""))
```

`raw` is whatever SQLModel attribute the facet column maps to. For every
column whose `cell_type` is `reference` (uuid FK), `boolean`, `number` or
`date`, `raw == ""` is compiled into a typed comparison
(`col = $1::uuid|date|boolean|numeric`). Postgres then fails to cast the
empty string and raises `invalid input syntax for type ...`, which the API
surfaces as HTTP 500.

This path is reachable from ordinary UI use: `column-filter-popover.tsx:51`
defaults `includeNulls` to `true`, and the popover submits the filter as soon
as the user unchecks a single value. Unchecking one value in any number, date,
boolean or reference column therefore breaks the whole grid.

Tests only cover text/asset columns:
`back/tests/test_renovation_api.py` (`col_011` around line 218, `col_016`
empty-values case around line 266, `__assetName` around line 278). No test
exercises `includeNulls` against a typed column, which is why CI stayed green.

Reproducing this while investigating the reported 500 revealed **two** typed
comparisons in the same function, both fatal:

- `includeNulls` on uuid/boolean/numeric columns — `invalid input syntax for
  type ...`;
- the date branch — `operator does not exist: date = character varying`, because
  the facet renders dates as ISO strings and they were bound as varchar.

**Fix** — build the empty bucket type-aware: only append `raw == ""` when the
underlying SQL column is textual (`isinstance(raw.property.columns[0].type,
String)`); otherwise just `raw.is_(None)`. Parse date selections back to `date`
with a `_facet_date` helper, mirroring `_facet_number`.

**Verification** — `uv run --directory back pytest -q tests/test_renovation_api.py`
with new cases covering number, date, boolean and reference columns; then a
manual `GET /api/renovation/plan/rows` against the freshly seeded plan with
`includeNulls: true` on a numeric column.

**Status note** — this is a *distinct* 500 from the one the user reported while
loading the plan. See [Follow-up](#follow-up-the-reported-500).

### AUD-02 — Seed workbooks are not actually ignored

**Evidence** — `.gitignore:32` ignores `/docs/seed/*.xlsx` only. `git check-ignore`
confirms that just `docs/seed/renovation_plan_vos_2027.xlsx` is ignored; the
`docs/seed/Планы/` subdirectory and every `.xlsb` file are not. `git status`
already shows `?? docs/seed/`, and `docs/seed/` is ~199 MB across 11 files.

A careless `git add -A` would commit the seed workbooks. This directly
contradicts `AGENTS.md`, which treats workbooks as local-only artifacts.

**Fix** — replace the single rule with a directory-level ignore
(`/docs/seed/`) or, if some artifacts must stay tracked,
`/docs/seed/Планы/` plus `*.xlsb`. Re-run `git check-ignore` on each file to
prove the rule bites.

**Verification** — `git check-ignore -v docs/seed/Планы/*` returns a rule for
every file; `git status` no longer lists `docs/seed/`.

### AUD-03 — Frontend `state` union never matches the API

**Evidence** — `back/src/renovation/service.py` serializes `RPlanState`, whose
wire value for the pending state is `pending_approval`. The frontend declares:

- `front/src/shared/api/renovation.ts:74` — `RenovationPlanVersion.state`
  (already correct: `"pending_approval"`),
- `front/src/shared/api/renovation.ts:100` — `RenovationPlan.state`
  (**wrong**: `"pendingApproval"`),
- `front/src/shared/api/renovation.ts:110` — `RenovationPlanRows.state`
  (**wrong**: `"pendingApproval"`).

Comparisons in `renovation-workspace.tsx` (the window-completeness path around
line 400 and the comparison-archive path around line 602) therefore never take
the pending branch, so pending-state UI affordances silently degrade. TypeScript
cannot catch this because the wrong literal is the declared type.

**Fix** — use one shared union type (import the wire literal once) and remove
the two wrong duplicates. Prefer deriving the type from a single
`type PlanState = "working" | "pending_approval" | "archived"`.

**Verification** — `bun run --cwd front typecheck`; grep for `pendingApproval`
returns nothing.

### AUD-04 — Seed script may not import in a prod image

**Evidence** — `back/src/scripts/seed_database.py:25-26` imports `openpyxl`
and `pyxlsb` at module scope. `back/pyproject.toml:11` and `:24` place them in
the dev dependency group. The production image is built with `--no-dev`, and
`.github/workflows/ci.yaml`'s `production` job runs
`docker compose -f infra/compose.ci.yaml run --rm --no-deps back python -m
src.scripts.seed_database --data-only`, which imports the module and would
raise `ModuleNotFoundError`.

**Status** — needs-run. The failure is reasoned from the import graph and the
build flags, not reproduced here.

**Fix** — move the workbook readers to optional runtime imports inside the
code paths that need them (lazy `import` guarded by a clear error message), or
promote the readers to main dependencies if production seeding is a supported
operation.

**Verification** — build the prod image and run the `--data-only` seed; then
run the full `--renovation-plan` import from a prod image.

## P1 findings

### AUD-05 — Dictionary saves fan out to N requests and N undo steps

**Evidence** — `front/src/shared/api/raw-materials.ts:203,221` and
`front/src/shared/api/renovation.ts:391,437,478` issue
`Promise.all(updates.map(...))`. Callers
(`raw-materials-workspace.tsx:673,679`,
`renovation-dictionary-section.tsx:463,469,471`) pass one entry per edited
cell, so a 100-cell paste becomes 100 requests and 100 separate undo actions
(one undo per cell).

**Fix** — add a batch endpoint that accepts an array of updates and writes them
in a single transaction/undo action; keep the single-cell endpoints for the
inline edit path. Update the frontend to send one batched request per save.

**Verification** — a test asserting one undo restores the whole batch; a
network assertion that a 100-cell save is one request.

### AUD-06 — Undo journal is a single rewritten JSONB blob

**Evidence** — `back/src/collab/persistence.py` keeps the undo/redo journal in
one JSONB row (`_stack`, `push_actions`, `mark_action_undone`, `clear_redo`),
capped at ~500 actions and mutated under `with_for_update`. Each edit rewrites
the whole blob, so write cost grows with journal depth and the row is a
contention point for concurrent editors.

**Fix** — move the journal to an append-only `collab_journal_entries` table
(action id, sequence, payload, undone flag) and maintain a small cursor per
session. Keep the JSONB blob only as a cache if profiling justifies it.

**Verification** — a write-latency test against a 500-action journal before and
after; contract tests in `back/tests/test_store_contract.py` still pass on both
transports.

### AUD-07 — Each rows window runs 2–3 COUNTs plus scans

**Evidence** — `back/src/renovation/service.py`: the window builder issues the
page query plus `total` and (when the asset filter narrows) `totalAll`
(`COUNT(*)` around lines 625 and 632). The same request also runs
`_baseline_boundary` and `_reference_labels` (a full scan of the reference
values table) on every call.

**Fix** — cache the total per (plan, filter-set) with an explicit
invalidation on writes; compute `totalAll` from a cheap count on a covering
index or derive it from plan metadata; memoize `_reference_labels` per plan
version.

**Verification** — `EXPLAIN ANALYZE` the window query before/after; assert the
number of statements per request drops from 4–5 to 1–2.

### AUD-08 — Export materializes rows before streaming

**Evidence** — `back/src/renovation/export.py` streams OOXML via `zipfile` +
`Queue` + daemon thread, but the row source first materializes the table with
`jsonb_strip_nulls(to_jsonb(renovation_plan_rows))` per row. Peak memory scales
with the whole plan.

**Fix** — drive the sheet writer from a server-side cursor / `stream_results`
execution so rows are produced lazily into the queue, and enforce a row cap
consistent with the dictionary export limits (`MAX_EXPORT_ROWS`).

**Verification** — export the full plan and record peak RSS; assert it stays
bounded and independent of row count.

### AUD-09 — Every WS ping re-resolves access and republishes presence

**Evidence** — `back/src/collab/ws.py:405` (`_handle_message`) handles `ping`
and `presence` by opening a session, re-running access resolution and
re-publishing the full member snapshot via
`back/src/collab/access.py` (`filter_messages`).

**Fix** — cache the resolved access snapshot per socket with a short TTL
invalidated by membership changes; send deltas instead of the full member list
for `presence`.

**Verification** — count DB queries per ping under a presence-heavy load test.

### AUD-10 — Rate limiter keyed by proxy IP, unbounded

**Evidence** — `back/src/main.py:37` (`_rate_limit_store`) keys on the
forwarded/proxy IP in a plain dict with no eviction, at 20 req/min. Behind a
proxy every client can share one key, and the dict grows without bound.

**Fix** — derive the client key from a trusted-hop-aware parse of
`X-Forwarded-For`, use a bounded TTL cache/store (e.g. the existing Redis
Valkey instance) and confirm the configured limit.

**Verification** — load test with `--expect-rate-limit`; assert distinct
clients behind the proxy get distinct buckets and memory stays bounded.

### AUD-11 — Local login can claim accounts without a password

**Evidence** — `back/src/auth/service.py` (`authenticate_local_user`) sets the
password for any user whose `password_hash IS NULL`, so the first caller to
present a login for such an account defines its password — an account-takeover
path.

**Fix** — only allow local login where a password is already provisioned, or
gate first-time password setting behind an explicit admin/invite flow.

**Verification** — a test asserting a password-less account cannot be claimed
by an arbitrary login attempt.

### AUD-12 — Grid monoliths and per-cell closures

**Evidence** — `front/src/shared/grid/raw-materials-grid.tsx` (from ~line 242)
and `front/src/features/renovation/renovation-grid.tsx` (from ~line 284) are
~2.2k-line components; per-cell render closures recompute across the whole grid
on each heartbeat/refresh tick.

**Fix** — extract a memoized cell renderer keyed by (row id, column id,
revision), split the toolbar/header/body, and use virtualization windows tied
to the existing plan-window state.

**Verification** — React profiler: commit count and duration for a heartbeat
tick on the full-size plan.

## Renovation plan at scale

The plan is the system's hot object. These findings are the ones the
optimization work should sequence first.

### AUD-24 — 216 nullable typed columns is the dominant cost

**Evidence** — `back/src/renovation/plan.py` defines `RenovationPlanRow` with
`col_003`…`col_218`, `Numeric(18,4)` for numbers, `Date`, `Boolean`, and FKs
into `renovation_reference_values` for `col_015/017/018/019/020`. The row is
also serialized to JSONB per row for read and export. At ~300k rows this is a
wide, sparse table with heavy per-row serialization.

**Direction** — anchor the hot, filtered, indexed columns as real columns
(keep them for filters/facets/indexes) and move the long tail into a single
`jsonb` payload column, or split into `plan_row_core` + `plan_row_values`
(one row per (row, column)). The split is the more scalable shape for 200+
columns and shifting schemas; the anchor-plus-JSONB shape is the smaller
change. Decide with a real measurement (AUD-25) before committing.

### AUD-25 — `_reference_labels` and `_baseline_boundary` run per request

**Evidence** — both execute inside `read_plan_rows` on every call
(`back/src/renovation/service.py`, `_reference_labels` defined near line 1395,
`_baseline_boundary` near line 1061). Combined with AUD-07's COUNTs, a single
page render costs several full-ish scans.

**Direction** — compute both once per plan version and cache (process-level
cache invalidated on write, or a small materialized table). Measure the
statement count and wall time per request first, then target ≤ 2 statements
per window.

### AUD-26 — `getRenovationPlan` full-plan fallback

**Evidence** — `renovation-workspace.tsx:400` calls the full
`getRenovationPlan(base.id)` whenever the window is "complete", and line 602
does the same for the comparison archive. At 300k rows an unfiltered full read
is the worst-case request in the system.

**Direction** — remove the full-read fallback in favor of paged windows, or
cap it hard with a server-side row limit and a clear "narrow your filters"
state. Audit every caller of `getRenovationPlan` for a paged alternative.

### AUD-27 — Facet queries lack an index strategy

**Evidence** — `read_plan_facets` groups by the raw column and collapses
NULL/'' into one bucket, sorting values in Python. There is no index plan
supporting arbitrary facet columns, so each facet selection can force a scan.

**Direction** — for the columns users actually facet on (the filterable
columns), add supporting indexes or precompute facet counts per plan version;
keep a facet result cache keyed by (plan, column, active filters).

### AUD-28 — Row writes recompute and re-serialize whole rows

**Evidence** — `update_plan_cells` (around line 1162) and `_recalculate_row`
(around line 1293) recompute formulas and re-serialize affected rows;
`apply_renovation_cell_value` (around line 1400) does the same for single
cells, and each write goes through the JSONB journal (AUD-06).

**Direction** — recompute only the dependency closure of the changed cell
(the formula engine already has topological order), and batch the journal
append.

## Follow-up: the reported 500

Added after diagnosis on 2026-09-28. The failure the user hit while loading the
«Пообъектный план» was **not** AUD-01. The backend log
(`logs/reportcollector.log`, 2026-09-28T06:12:52Z) shows:

```
File "/app/src/renovation/service.py", line 1092, in _plan_row_read
    renovation_id, missing = _row_renovation_id(row, asset, label_map)
File "/app/src/renovation/service.py", line 1120, in _row_renovation_id
    result = calculate_renovation_id(_renovation_id_input(row, asset, label_map))
File "/app/src/renovation/renovation_id.py", line 202, in calculate_renovation_id
    _validate_fixed_ascii_digits(defect_number, 7, _invalid_defect_number(defect_number))
src.renovation.renovation_id.RenovationIdError: некорректный номер ДВ `101`: ожидаются ровно семь цифр
```

**Root cause.** `_row_renovation_id` recomputes `col_003` at read time for every
row whose stored `col_003` is empty. The reseeded workbook contains rows whose
`col_023` (defect number) violates the seven-digit legacy rule, so
`calculate_renovation_id` raises, and a single bad row 500s the entire window
(the whole 1000-row page). The seed fixture only used valid seven-digit numbers,
so CI stayed green.

**Fix.** A guard (`_safe_renovation_id`) that falls back to the `<NULL>`
placeholder and reports `missing_components=("invalid_components",)`; applied at
every call site, including `read_plan_export_data` → `_sparse_row_renovation_id`,
which had the same exposure on the export path.

**New findings from this diagnosis:**

- AUD-31 — `_sparse_row_renovation_id` (export) shared the unguarded call and
  would 500 the XLSX export on the same rows. Confirmed, fixed.
- AUD-32 — `RenovationPlan.state` / `RenovationPlanRows.state` in
  `front/src/shared/api/renovation.ts` (lines 100, 110) declared
  `"pendingApproval"` while the API sends `"pending_approval"`, so the pending
  branches never matched. Confirmed, fixed. (`RenovationPlanVersion.state` at
  line 74 was already correct.)
- AUD-33 — window payloads carried all 217 column keys including the ~197 empty
  ones per row. Confirmed by measurement and fixed; see
  `docs/RENOVATION_PLAN_PERFORMANCE.md`.
