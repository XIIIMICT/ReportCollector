# Grid (frontend, revo-grid)

Sections, in order: Forms and columns (`grid-config.ts`) · Clipboard · Selection · Pinned header and scrollbars · Coordinates: sorting and filtering · Presence and tooltips · Responsive layout · Status summary and view strip · Misc · Ремонт (plan grid, split into `###` topics) · КППК.

Main code: `front/src/shared/grid/` (`raw-materials-grid.tsx` — the grid component, `grid-config.ts` — forms/columns config, `grid-edit.ts` — edits, `grid-editors.tsx` — cell editors, `section-tabs.tsx` — form tabs). Orchestration: `front/src/features/raw-materials/raw-materials-workspace.tsx`.

## Forms and columns (`grid-config.ts`)

- **All grid headers wrap text.** The shared native-header selector includes
  `.rgHeaderCell` so it overrides RevoGrid's more specific `white-space: nowrap`.
  Leaf and grouped headers use `white-space: normal` and `overflow-wrap: anywhere`;
  long words wrap within narrow columns instead of widening the header or being
  forced into a single line. Header row heights remain controlled by the grid.

- `SectionId`: `materialMovement` («Движение»), `rawMaterialPrices` («Цены»), and the dictionaries `rawMaterials`, `assets`, `deliveryBases`, `users`. `MAIN_SECTIONS` = movement+prices; dictionaries are admin-only. The `users` table shows «Время последнего входа» (`lastAuthenticatedAt` from `app_users`, read-only `datetime` column) — the last successful authentication (Keycloak or local), null until the user has logged in. The «Сбросить пароль» action column is hidden when Keycloak is enabled (passwords are managed in Keycloak) — flag flows through `GridColumnContext` into `getVisibleDescriptors`/`editableFieldKeys`/export. The profile modal hides its password-change fields the same way (it fetches `/api/auth/config` itself; if the config is unknown it keeps the fields).
- `ColumnDescriptor`: key, label, width, kind (`text|number|boolean|asset|assetsMulti|basis|datetime|calculated`), `fixed` (pinned, non-editable), `path` (nested header, e.g. «Потребность / План, т»), `adminOnly`, `exportable`, `readOnly` (editable in no row — e.g. the renovation users' `email`, which only the creation dialog sets), `allowsNull` (a NULL is a legal state — the boolean checkbox then cycles three ways, see below).
- Merged headers (`ColumnGrouping`) are built from `path`; editors: `reference` (single pick from `source`), `multiAssets` (multi-pick), booleans — one native checkbox template shared by every grid (see «Boolean cells» below).
- Each row is a `GridRow`: id, `rowState` (`unchanged|new|deleted`), `changedFields`, `isDeleted`, `canonicalCells` (canonical cell keys), `isPlaceholder` (the trailing «добавить запись» row; the users dictionaries have none). Its row-header button shows **«+» instead of a number** («Добавить строку» tooltip) — same as the renovation plan grid.
- **Users are created through a dialog, not the placeholder row.** The `users` dictionaries of both projects (and only they) create records through the shared `AddRecordModal` (`front/src/shared/ui/add-record-modal.tsx`) opened by the «Добавить пользователя» action-bar button (the same `Plus` icon as every other dictionary). The trailing placeholder row is not rendered for `users`. The modal's fields are role-dependent: in «Ремонт» the role picker drives which fields show — the «Дирекция» for `block_owner`/`asset_worker`, the «Активы» picker only for `asset_worker` (admin/approver implicitly cover every asset, so they show neither). The modal validates (email/ФИО/role/block/assets) and keeps itself open with the message on failure; a successful create refreshes the grid and offers Ctrl+Z (the server journals it like any dictionary create).
- Default sort: raw-material items first, then assets; placeholder/deleted always at the end (`placeholderLastCellCompare`).
- **Boolean cells — one control everywhere.** `nextBooleanValue` (`grid-config.ts`) defines the click cycle, and `booleanCellTemplate` renders a native `<input type="checkbox">` inside `label.report-cell__checkbox` (centered by CSS) — the same markup in «Сырьё», КППК and «Ремонт», no custom button component:
  - **plain column** (`allowsNull` off — «Доступ к проекту», «Админ»): `false ⇄ true`; the value is never cleared (the dictionary columns are NOT NULL), and an empty value still renders an unchecked box;
  - **nullable column** (`allowsNull`, the plan's `col_202`/`col_212`/`col_215`): `пусто → Да → Нет → пусто`. A `null` renders as an **empty cell — no checkbox at all** (`report-cell__checkbox--empty`, the whole cell stays clickable); `true`/`false` render the normal checked/unchecked box. A click on the unchecked «Нет» box CLEARS the value — the same result as `Delete` — and the empty cell's first click checks it. No `indeterminate` state: only «Да»/«Нет» show a checkbox.
  The plan's descriptors set `allowsNull` from the form schema (`field.allowNull`, `back/src/renovation/form_data/renovation-form.json` → `validation.allowNull`); the backend already accepts and stores `null` for a boolean cell (`_coerce_cell`). Every change goes through `onBooleanChange(row, field, value: boolean | null)`. Export writes `Да`/`Нет` for booleans and an empty cell for `null`.
  **Commit on `click`, never on `change`.** The handler calls `event.preventDefault()`, which cancels the native toggle (and therefore `change`): the checkbox never flips locally, so a clearing click (`false` → пусто) does not flash a checked box for a frame before the server answers. The box's state always comes from the row value on the next render.
- Form reads: «Движение» — `GET /movement?report_month=`, «Цены» — `/prices`; dictionaries — their own GETs. Edits — `PATCH /movement`, `/prices`, `updateDictionaryCells`; one edit = a batch `{rowId, field, value}`.
- **«Бизнес-план, т» in «Движение» is a projection from «Цены», non-editable; in «Цены» business-plan edits go to `RawMaterialPrice` and are not "projected" onto other forms.**

- **Dropdowns: one `SmartSelect` everywhere** (`front/src/shared/ui/smart-select.tsx`). Instead of using HeroUI's `Select`/`Autocomplete` directly, every dropdown goes through it: **`≤ threshold` options (5 by default) render a plain `Select`, more render a searchable `Autocomplete`** — both are the same react-aria `Select`, so `value`/`onChange`/`multiple` behave identically whichever wins. `multiple` is independent of the count (a short multi list is still a `Select` with `selectionMode="multiple"`). Every instance **opens on hover** and closes ~200 ms after the pointer leaves both the trigger and the popover (coordinate-based, not `mouseleave` — an open popover's overlay fires structural leaves while the pointer is still). Extra props: `threshold`, `forceSearchable`, `embedded` (in-cell editors: hidden trigger, open on mount, Escape → `onDismiss`), `anchor` + `defaultOpen` (the column filter's anchored popover), `emptyOptionLabel`, `popoverFooter`, `renderListbox` (a subclass keeps its own list), `compactLabel` (short trigger text below lg).
  - `SearchAutocomplete` (toolbar filters) forwards `allOption`/`allValue`/`nullOption` to `SmartSelect` — a toolbar's «Все блоки» / «Все варианты» row is a PROPERTY now, never a fake entry in `items` (a fake entry rendered below the rule and had no separator). Picking it reports `null` (= no constraint).
  - The in-cell `SelectEditor`/`MultiAssetEditor`/`ReferenceEditor` (`grid-editors.tsx`) are thin adapters over it (the reference editor's «Не задан» is a `nullOption`).
  - Embedded mode hides `.grid-autocomplete-editor__hidden-trigger` for BOTH
    Select and Autocomplete. Short reference lists must not expose a second
    input/trigger in the cell; only the anchored dropdown is visible.
  - Both grids register editors with `shared/grid/react-editor.tsx`. RevoGrid's
    stock React adapter synchronously unmounts its nested root during grid
    removal, which React 19 rejects inside a parent commit. Our bridge detaches
    each root's own mount immediately and unmounts that root once in a microtask;
    ref cleanup and disconnectedCallback are idempotent, even if the host is reused.
  - **Special rows are properties, not hand-rolled items**: `nullOption={{ label, present, count? }}` pins a «Пустые»/«Не задан» row (selecting it reports `null`) and `allOption` pins a «Все варианты»/«Выбрать все» row (`allValue` is the sentinel a single-select reports; in a multi-select picking it selects every real option). Both sit ABOVE the values, in that order, with an automatic `<Separator class="smart-select__separator">` between them and the values — emitted only when both sides are non-empty, so an absent special row leaves no stray rule. `count` renders the `(N)` suffix the filters show («Выбрать все (248)»).
  - `ColumnFilterPopover` uses the `anchor`/`defaultOpen`/`forceSearchable`/`renderListbox` slots: its «Выбрать все (N)» + «Пустые» + paged values list lives in the callback (the master-toggle logic — «stays checked while some values are unchecked» — has no generic equivalent), everything else (anchor trigger, hover/open state, search field, separator style) comes from `SmartSelect`.
  - **The option tick sits LEFT of the label** (`.smart-select-popover .list-box-item__indicator`): HeroUI positions it `absolute` at the row's right edge and reserves only `pe-7`, so a long value runs under the tick. The override puts it back in the flex flow (`order: -1`) and must reset **`translate`** — HeroUI centers it with the modern `translate` property, not `transform`; a `transform: none` alone leaves the box lifted above the baseline. The row `gap` drops 0.75rem → 0.5rem so the tick-to-text space reads tighter.
  - **Panel width is intrinsic, independent of the trigger.** `.smart-select-popover` uses `width: max-content; min-width: 0` and a viewport-only maximum. This overrides Select's trigger-based minimum and Autocomplete's trigger-based width/maximum. No canvas measurement, 224px floor or per-project cap: the browser measures the real font, indicator, row/list padding and the widest rendered line (name and description are separate lines). Search inputs shrink into the resulting panel instead of imposing their native input width. The same rules apply to custom lists and special rows.
  - Tests run against happy-dom; `test-setup.ts` installs `FocusEvent` because react-aria's `focusSafely` constructs one when it moves the virtual focus onto an option.

## Clipboard

KPPK realization and cost rows are derived from dictionaries/source data: their action bars
does not render row deletion (including in the compact action menu).

Workspace bindings use `shared/ui/use-grid-clipboard-actions.ts`: publication,
copy and paste handlers keep stable identities and resolve the current grid ref
at click time. Parent state accepts a publication only when `canPaste` or its
handlers changed. Comparing only the boolean would retain another tab's actions;
publishing fresh closures from every render causes a grid/workspace effect loop.
Both grids use `parsePastedText` for trailing Excel buffer cleanup. Shared
event-only history/export flows live in `history-action.ts` and
`table-export-action.ts`; they do not own form/session scope or parent effects.

Shared UI boundaries: `workspace-layout.tsx` owns layout only (card/body and
fullscreen reveal panels); `workspace-feedback.tsx` and `grid-loading-skeleton.tsx`
own common error/initial-loading views. Keep lifecycle, permissions, virtualized
grid geometry and pending-write serialization project-local. Preserve callback
identities feeding grid effects/columns; tests must cover rerenders and tab
switches, not only equal boolean values.

KPPK «Пользователи» is admin-only. It uses the shared grid and add-record modal:
email/FIO, administrator role, empty read-only ДЗО association, project access,
last sign-in and audit columns. Keycloak owns identity/password fields in SSO
mode. Creation provisions inactive memberships in other projects, without
touching their roles/assets. Self-deletion and deletion before access revocation
are refused. Changes and lifecycle undo are scoped to `kppkUsers`.

In all three users dictionaries the signed-in person's own row is view-only
(`GridRow.readOnlyRow`): text editors, checkbox changes and paste are disabled;
the HTTP endpoints, lease authorization and journal replay refuse self-edits
too. This does not disable the separate profile form. KPPK's tab strip places
the shared `Tabs.Separator` between «Реализация» and its dictionaries.

The form-status tooltip renders participants as an unordered list (including
the current user even when alone), with the current user last. The standalone
«Выделено» block has the same blank-line spacing after presence as before the
row/column statistics group; a participant's remote selection stays beneath
their name inside the same list item.

`raw-materials-grid.tsx`, "clipboard" section (functions `copySelection`, `pasteIntoSelection`, `cutSelection`, `buildCopyText`).

- **Copy (Ctrl+C)** — by value: numbers as-is (`,` for decimals), multi-dictionaries — joined with `,`; the copy goes to the system clipboard (`navigator.clipboard`).
- **Paste (Ctrl+V)** — the whole path goes through `rangeeditapply` → `beforeRangeEdit`, so locks/validation and undo/redo work uniformly:
  - Dictionary fields: single dictionary — the value must match an option; multi (`assetsMulti`) — `split(",")`, **each** value `str.strip()`-looked up among options, otherwise the paste is rejected (toast). When pasting dictionary rows, values are mapped to **existing UUIDs** (by value after strip).
  - Sizes: one cell selected → paste everything starting from that cell; ≥2 cells selected → paste only into the selected range: if the pasted range is bigger — it's **trimmed** by the range (toast), if smaller — pasted as-is, other cells untouched.
  - **Excel buffer**: trim trailing empty rows and columns (Excel puts a trailing `\n`) — otherwise an extra empty cell below overwrites a neighbor.
  - **Numbers**: any Unicode whitespace is accepted as a thousands separator (regular space, NBSP, narrow NBSP — Excel uses different ones), `,` becomes `.`. Front: shared `parseNumericText` (`front/src/shared/grid/grid-edit.ts`, used by both grids); back: `coerce_number` (`raw_materials/service.py`) and the seed parser — keep them in sync.
  - After paste the selection moves to the pasted cells and goes to presence.
- **Ctrl+X** — like Ctrl+C but clears the source cells (empty value; multi — empty list; boolean fields skipped). Through the same `rangeeditapply` → busy cells are skipped, the operation lands in undo/redo.
- **Hotkeys — by `event.code`** (`KeyC/KeyV/KeyX/KeyZ/KeyY/Delete`), otherwise broken with the Russian layout. Ctrl+Z/Y — undo/redo (server-side stack, see `docs/COLLAB.md`). Ctrl+Delete — opens the delete confirmation dialog (same dialog as the action-bar button; dictionaries here, plus the renovation plan/dictionaries), active only when deletion is possible. **Undo race guard:** the workspace keeps the in-flight commit promise in `pendingCommitRef` and `runUndo`/`runRedo` await it first — a Ctrl+Z pressed right after Enter would otherwise reach the server before the PATCH journaled the edit and silently do nothing (observed as an e2e flake under load).
- The paste button («Вставить») only works when the buffer is compatible with the selection (`canPasteRange`) — also through the visible row source.

## Selection

- **Ctrl+A — fully custom**: a `document` handler in the capture phase with `stopImmediatePropagation` (kills revo-grid's built-in select-all, which draws three torn frames — header/data/bottom). Selects one contiguous range over the data cells, **without headers and without the «добавить запись» row**. The range is derived from the **visible source** (sorting/filtering applied), not the raw `rows` array. On the «Ремонт» plan Ctrl+A is disabled entirely (see below).
- **Programmatic selection — only through the grid's public API**: `grid.setCellsFocus(start, end)` + `grid.refresh()` (without `refresh` Stencil doesn't redraw the overlay). Reset — `grid.clearFocus()` + `grid.refresh()`: the store empties, but without `refresh` the old range rectangle stays visible. **`store.setRange` doesn't exist** (in `revogr-overlay-selection` there's a raw observable without methods) — it's dead code, don't use it.
- Row selection (click/shift/ctrl on the row number) **resets** the cell selection (`clearGridSelection`) — both state and the visual frame. The shift-range maps indexes through the visible source too (sorting/filtering), like everything index-based. **Order matters**: the range is cleared **before** `setSelectedRowIds` — the row selection rebuilds `columns` (selectedRowIds is a `columns` dependency) and revo-grid's `columnChanged` captures the still-live focus into `pendingColumnFocusRestore`, which `restoreColumnFocusAfterRender` then re-applies as a single-cell range (its guard can't match an empty store). `clearGridSelection` also drops the stale restore for the same reason.
- **Escape on the «Ремонт» grid additionally bumps `selectionEpoch`** (a `columns` memo dependency) **after** `clearGridSelection`: with a plain range (no row selection) `setSelectedRowIds([])` changes nothing, no columns rebuild happens, and the selection overlay does **not** reliably repaint on a bare store change — the rectangle stays until the next keypress. The forced rebuild repaints the overlay from the already-empty store (safe: `columnChanged` finds no focus to restore — same reasoning as row clicks). The «Сырьё» grids don't need it: their selected-row classes live in `rowHeaders`, not `columns`, and their overlay repaints correctly on `clearFocus` + `refresh`. Escape fires when the grid is the event target **or still holds a live range** (`selectionRangeRef` / `lastRangeRef`): a cell click can leave the focus on `body` after revo-grid's re-render, and requiring a grid target made Escape dead in exactly that case — with no target and no range the key belongs to whoever owns the focus (menus, dialogs). Escape and the clipboard shortcuts ignore presses from inside text editors — checked via `composedPath` (`isFromTextEditor`, `front/src/shared/keyboard.ts`): revo-grid's built-in cell editors are shadow-DOM inputs, invisible to `document.activeElement`.
- A mouse-dragged selection is sent to presence **only on completion** (`setrange`), not live.

## Pinned header and scrollbars

- The «Закрепить заголовок» option (grid options menu, ⋮) is **on by default** (`headerPinned` state in `raw-materials-workspace.tsx`). The «Сырьё» grids: pinned — the grid fills the shell (`revo-grid-shell--pinned`), revo-grid scrolls internally; unpinned — an external vertical scroller plus a custom horizontal strip (`revo-grid-external-scrollbar`), the grid sized to its content (`--grid-content-height`). **The «Ремонт» plan is different**: it always fills the shell and scrolls internally (the native vertical strip; the custom external horizontal strip at the bottom); the header overlay lives in a flex slot whose `margin-top` animates to `-var(--renovation-header-levels-height)` when unpinned (`renovation-grid__header-slot--hidden`) — the grid simply grows (revo-grid re-measures), so toggling the pin never reloads the table. **Unpinning hides only the 11 header levels** (they fade out via `.renovation-grid__header-slot--hidden .renovation-grid__header-cell`); the column-number strip and the «№» corner stay visible — they sit in the slot's bottom band (24px) and land right above the pinned totals row, so the numbers remain readable with the header off. The old external 11M-px vertical scroller (content height of 306k rows) was removed: with the Infinity Scroll source it froze the renderer.
- **Scrollbars are the browser's native ones, no custom styling.** revo-grid hides its raw viewport scrollbars (`scrollbar-width: none`) and renders `revogr-scroll-virtual` strips whose *own* native scrollbars are the visible bars — they're real light-DOM elements, and revo-grid sizes them to the measured system scrollbar width, so pinned and unpinned bars naturally match. **Landmine**: revo-grid's light theme sets `color-scheme: light` on the host → native scrollbars render light even in the app's dark theme; `globals.css` fixes it with `.dark .raw-materials-grid { color-scheme: dark }` — keep that override if the `theme` prop changes.
- Scrollbars appear only when there's overflow (native `overflow: auto`); `revogr-scroll-virtual` collapses to 0 size without overflow (revo-grid sets its min-size to 0 in `componentDidRender`). Without overflow the «Сырьё» external strip is hidden via `revo-grid-shell--no-hscroll` (`hasHorizontalOverflow` state) — no dead 17px gap under the last row; the plan's native horizontal strip collapses the same way (`--no-hscroll` + the forced-height rule below).
- **Scrollbars match the plan in every form.** The custom external strip
  (`.revo-grid-external-scrollbar`) is the visible horizontal bar in BOTH pin
  states now (not just unpinned); it is inset by the vertical scrollbar's lane
  (`verticalScrollbarLane`, read from the vertical strip's inline `min-width`), so
  the two bars stop where the other begins instead of crossing in the bottom-right
  corner. revo-grid's native horizontal strip stays hidden in both states. The
  vertical strip starts BELOW the header (`top` + `height` from the shell's
  `--grid-header-height`), so it no longer runs across the header cells' right edge
  — the plan offsets it below its summary row the same way.
- **Live column resize (every grid except the renovation plan's overlay).** revo-grid's own
  resize handle commits the new width only on pointer-up (its `ResizeDirective` forwards
  `onResize` for the `end` event alone), so the boundary used to jump after release. The
  shared `raw-materials-grid.tsx` now drives the drag itself: a capture-phase `pointerdown`
  on a `.resizable-r` handle resolves the column from the header cell's `translateX` offset
  against `getColumns()`, and every `pointermove` applies the width through
  `grid.updateColumns([{ prop, size }])` — the grid re-renders live, exactly like the
  renovation plan's overlay. The width is persisted on pointer-up (`resizedWidthsRef`, keyed
  by `widthKeySection` + prop) since the programmatic update skips `onAftercolumnresize`.
- **The plan's strips** (`renovation-grid-shell`): the native horizontal strip is **hidden** (`height: 0 !important` in both pin states — Chrome draws it too thick); the custom external strip (`revo-grid-external-scrollbar`, 17px, own webkit styling, hidden via `--no-hscroll` when everything fits) is the visible bar — its spacer carries the full content width, `onScroll` drives `grid.scrollToCoordinate`, the grid's `rgCol` viewport scroll syncs it back, and **wheel over it scrolls sideways** (JS, see below). **The two bars must not overlap in the bottom-right corner** (the full-width strip and the overhanging vertical strip intersected there — a rendering glitch the users reported): the native vertical strip starts **below the pinned summary row** (`top: var(--renovation-summary-height)`) and **ends at the grid's bottom edge** — `height: calc(100% - var(--renovation-summary-height)) !important`, since the library's plain `height: 100%` would stick 36px past the grid, over the strip's right end; the horizontal strip's `right` edge is inset by the vertical strip's **reserved lane** (`verticalScrollbarLane` state, measured from the strip's inline `min-width` — the library's reserved system-scrollbar width, 0 on overlay-scrollbar platforms), so each bar stops where the other's lane begins. **Landmine (raw grids, unchanged):** in unpinned mode BOTH internal scrollbars are hidden there — zeroing the strip sizes (`width/height: 0 !important` + min-*), not `visibility: hidden` alone (revo-grid sets an inline min-size; Firefox paints the scrollbar of a hidden container).

## Coordinates: sorting and filtering (the most important landmine)

Plan facet responses include `nullCount` on every page. During mixed-version
deployments, an absent/non-finite count is hidden (not replaced with a fabricated
zero); later pages cannot turn the displayed count into `NaN`.
Selection details quote the entire header hierarchy, leaving coordinates outside:
`«Идентификационный код работы/ремонта» (столбец 2), строка 42`.
The internally scrolling renovation plan reserves 17px for the external horizontal
scrollbar in both pinned and unpinned header modes, preventing Chrome from
covering the final row. Unpinned dictionaries retain their external scroll layout.

Under sorting/filtering the screen row index **doesn't match** the `rows` index (the source array is unsorted). Anything mapping "index → row" must use **`getVisibleRows()`** (`grid.getVisibleSource("rgRow")` — the current sorted/filtered source): paste (building `models`), cut, copy (including the context menu), presence (my selected keys), `canPasteRange`. Otherwise values are committed to the wrong row → fake asset "deletions" → RESTRICT error (symptom: «ошибка удаления актива» when pasting on a sorted sheet).

## Presence and tooltips («На форме»)

- The collab presence and the selection/filter summary are one merged component — `FormStatus` (`front/src/shared/ui/form-status.tsx`) — in the **bottom footer**, left of the action bar; the presence helpers live in `front/src/shared/collab/collab-presence.ts` (`membershipSummary`, `memberDetail`, `memberSelectionLabel`, `shortName`). Inline it is a row: the status badge (dot) on the **left, vertically centered** against the stacked lines `<b>На форме:</b> …` / `<b>Выделено:</b> …`; the HeroUI tooltip spells out «Выделено» and «Строки»/«Столбцы» first, then the member presence list. «На форме» uses last names only, **«вы» is lowercase**, role «админ» (not «Администратор»), for an asset worker — the **concrete asset list**; full FIO and cell ranges — only in the tooltip.
  **When collaboration is off or still connecting there is no member list** — the footer shows the state alone («Совместное редактирование недоступно», «Подключение к совместному редактированию...»), set in bold (`.form-status__presence--bold`), with NO «На форме:» prefix. The prefix belongs to an actual presence list.
- **A remote member's cells are marked by ONE shared rule**, not a per-project copy: the grid code (shared `grid-config.ts` for the dictionaries and `renovation-grid.tsx` for the plan) adds `report-cell--remote-locked`, and `globals.css` styles `.rgCell.report-cell--remote-locked` once (warning tint + a 2px inset outline). Every cell carries its own box — a perimeter-only outline was tried and dropped: it needs four neighbour lookups per cell on every render and reads the same for the small dictionary grids.
- **Top vs bottom panels:** the top (toolbar + view strip) holds view controls — the version picker («Рабочая версия»), tabs, the asset/block filters (renovation plan), the display toggles, the reset dropdowns and fullscreen; the bottom footer holds the presence/selection summary (`FormStatus`) and the actions — undo/redo/copy/paste/export/add/delete/submit/approve (the Excel export lives in the bar; `ViewStrip` renders with `hideExport`).
- **One rhythm for the whole top toolbar — the PARENT spaces its children, never the children themselves.** `.table-toolbar > *` (single-row toolbar: «Сырьё», «Ремонт») and `.table-toolbar__row > *` (a stacked toolbar's row: КППК) both give every DIRECT child the same `margin-right: 0.75rem`, with `:last-child` at 0. So the tabs, the view strip and whatever sits to their left (block filter, «Настройка акциза», version picker) share one gap, and the last control ends flush with the card edge. Consequences worth knowing:
  - a per-project control must be a **direct child** of its toolbar row, not an extra wrapper — a wrapper takes the spacing onto itself and leaves the control glued to its neighbour;
  - the spacing is a **`margin`, not `gap`**: `gap` also counts a collapsed control (`.toolbar-collapse--hidden` stays a zero-width flex item), which pushed the tabs inward whenever КППК hid the «Настройка акциза» switch. A margin is dropped by the hidden box;
  - a stacked toolbar's own rows span the full width (`.table-toolbar--stacked > .table-toolbar__row { margin-right: 0 }`), since their children carry the rhythm.

  This was the source of a long series of "tabs are inset / the strip stops short of the edge" bugs: three projects, three slightly different wrapper trees. Keep the tree identical.

Press is open-only: on touch the synthetic mouseenter has already opened the menu, a toggle would close it instantly; and the pointer-out close only arms after a real pointermove, so a keyboard-opened menu is never killed by a stale pointer position. **Closing is pointer-position based (`getBoundingClientRect` polling on `pointermove`), NOT `mouseleave`** — while a modal popover is open, react-aria sets `inert` on everything outside it, the trigger stops being hit-testable, the browser fires a phantom `pointerout`, and a `mouseleave`-based close loops forever (open → inert → phantom leave → close → un-inert → re-enter → open). Escape closes in capture phase and suppresses the hover reopen until the pointer physically leaves the trigger (otherwise the closing menu un-inerts the trigger and the still-hovering pointer re-opens it instantly).
- `useMediaQuery` (`front/src/shared/hooks/use-media-query.ts`): starts `false` (SSR-safe), subscribes via `matchMedia`. **Landmine:** React implements onMouseEnter over `mouseover`/`mouseout` — dispatching synthetic `mouseenter` doesn't fire it (test hover-open with `mouseover` or real pointer events; `front/e2e/hover-dropdown.spec.ts` does exactly that with `page.mouse.move`).
- **Tiny tooltip triggers (the collab dot):** `locator.hover()` can miss an 8×8 trigger (its pointer move can land outside / get eaten), so the collab e2e opens the tooltip with an explicit `page.mouse.move` from a distance (`hoverCollabBar` in `front/e2e/collab.spec.ts`); the dot's own hit area is padded in CSS to ~18px.
- **Header support control** (`front/src/shared/ui/support-button.tsx`, `.support-link` in `globals.css`): «Связаться с разработчиком» sits after the profile pill. Collapsed it is the `HeadsetHelp` icon; the label is a child whose `max-width` animates from 0 on `:hover` / `:focus-visible` (focus matters: an icon-only control would otherwise be unlabeled for keyboard users), and `--pinned` keeps it open — the «нет доступа к проекту» page renders it expanded. ### Header overlay, columns and clipboard

- **Overlay column header.** The Excel form has 11 header levels (`meta.headerRows`), which revo-grid's native header cannot render. The grid's own header is hidden and the page draws the levels itself: `.renovation-grid revogr-header { display: none !important }` hides **both** `revogr-header` elements — the main column header **and the corner header inside `revogr-row-headers`**. Both live in their own `revogr-viewport-scroll` whose `.inner-content-table` is a flex column (header + `.vertical-inner`), so hiding only one would offset its data area by the header height and misalign the «№» column with the data rows; hiding both makes both data areas start at y=0. The overlay (`.renovation-grid__header`, height = the 11 header levels + the 24px column-number strip; 288px by default) is positioned over the grid, tracks the horizontal scroll **imperatively** — `onViewportscroll` writes `translateX(-x)` straight onto a ref'd `.renovation-grid__header-body` (no React state per tick: a `setScrollLeft` on every scroll tick re-rendered the whole grid and made horizontal scrolling janky; the inline transform is left out of the JSX so React re-renders don't reset it), has an opaque 52px corner matching `ROW_HEADER_WIDTH` (its own box-shadow closes all four edges, including the right border over the data row headers), and per-column resize handles (pointer capture → live `overlayWidths`, committed to `localStorage["renovation:colWidth:<dbName>"]` and to the grid columns on drop), plus one **horizontal handle per header level** on the level's bottom boundary (6px, `row-resize`; the column handles are rendered after them, so at a crossing the column resize wins and the level boundary stays grabbable a few pixels away). Dragging a horizontal handle changes the height of the level ABOVE it — the Excel row-height gesture — clamped to 12–400px: the overlay geometry follows live (`levelOffsets` — the level tops and every cell's height derive from it, the grid columns don't depend on it so revo-grid never rebuilds) and the array is persisted to `localStorage["renovation:headerLevelHeights"]` on drop; the «Сброс ширины столбцов и высоты строк» entry clears it (`resetColumnWidths`). **Handles exist only on VISIBLE boundaries**: the header cells tile the levels, so a boundary inside a merged (spanned) cell draws no line — the handles are `clip-path`-limited to the bands where a cell actually ends (a column handle to the y-bands of the cells ending at it plus the number strip AND the totals row — the handle's explicit `height` overhangs the header body so the bar reaches the bottom of the aggregating row, like the boundary line; a level handle to the x-bands of the cells ending at that boundary, `mergeBands` + `handleClipPath` in `renovation-grid.tsx`). Without the clip the resize bars popped up over the interior of merged cells (the reported glitch); the clip also limits the hover highlight and the `col-/row-resize` cursor, and hit-testing respects it. Widths and level heights are persisted to `localStorage` when the drag ends — and, as a fallback for a drag whose `pointerup` never reaches the handle (lost capture, released outside the window), a window-level `pointerup`/`pointercancel` listener commits and persists it (`endResize`/`endLevelResize` read the live preview from refs, so the listener can stay identity-stable). **Landmine**: the handles live in `.renovation-grid__header-body`, which is absolutely positioned with all-absolute children — it collapses to 0 height unless it gets an explicit `height: headerHeight` inline style; without it `top: 0; bottom: 0` on the handles resolves to a 0px-tall, unclickable strip. **Full-height columns with no level-0 cell above them are raised to the top** by the overlay: in the Excel «Идентификационный код работы/ремонта» (position 1) and «Примечание» (position 215) start at row 7 (level 1) with an empty level-0 slot above them (the three responsibility-block rows cover positions 2–214). The overlay computes the union of level-0 spans and lifts uncovered cells to `top: 0` with `height: (level + rowSpan) × 24` — otherwise the cell's top border sits at the blocks' bottom line ("as if it belonged to its own top (Техническая дирекция) block") and «Примечание» shows a spurious second top border with its right border missing in the top corner.
- **Column-number strip.** Under the 11 levels the overlay draws the source workbook's helper row: a 24px muted strip (`renovation-grid__number-cell`) carrying each visible column's **number in the form** — `meta.fields[].ordinal` minus 1, so «Предприятие» = 1 (the workbook counts the row-number «№» column as 1; the app numbers the data columns from the first one), «Цех» = 4 … `col_217` = 216 — directly above the pinned totals row. The ordinal, not `position`: `position` is the app's field index, and the hidden `col_218` sits at position 23 — numbering by it skipped 23 (the reported bug). The workbook numbers are continuous whatever is hidden. It slides with the header (the same `headerBody` translate), resizes with the columns and stays empty for the service columns, and **remains visible when the header is unpinned** (see the pin bullet above). **Hovering a number shows its column's header chain in a HeroUI Tooltip** (`headerChainByProp` → `.renovation-grid__number-tooltip`): the cells covering that column from the top level down, each on its own line with «↓» between them — the same texts the overlay draws (canonical block labels included, consecutive duplicates dropped). The cell carries `data-column` and is hoverable (`pointer-events` enabled; the merged cell's part over the totals row therefore swallows the pointer there — the totals cells have no hover behaviour of their own). The bottom-most header cells drop their bottom line (`renovation-grid__header-cell--bottom`) so the strip's top line is the only border between them. **With the header unpinned** the level funnels vanish with it, so the number cell carries the same funnel (rendered only when `!headerPinned`; a service column has no number and no funnel) — the column filter stays reachable with the header off, and the number text shifts left by the funnel's 24px exactly like the header labels. The chain text in the tooltip is **centred** (`text-align: center`). The popover is driven MANUALLY (`isOpen` + an invisible trigger at the cell's coordinates) and is **remounted on every hovered column** (`key={numberTooltip.column}`) after a one-frame close (`setNumberTooltip(null)` → `requestAnimationFrame` → open): sweeping the pointer along the strip used to leave the previous box visible with the next column's text, because react-aria keeps its own anchor/open state and re-anchoring the moved trigger in the same commit is unreliable. The grid root also listens to `pointerout` (closing when the pointer leaves the root) alongside `pointerleave`, so a fast diagonal exit out of the strip cannot skip a `pointermove` and strand the box.
- **Columns** come from `meta.fields` (prop = `dbName`), widths from `localStorage`/defaults by cell type, `min/maxSize` 60–600. A synthetic **«Предприятие»** column (`__assetName`, default 220px, resizable like the plan columns — its width persists under `localStorage["renovation:colWidth:__assetName"]`) is always prepended: it shows the row's asset and is **read-only** (rows are added through the «Добавить строку» dialog, all columns are set after); its overlay header cell spans all 11 header levels (264px). The form's own `col_002` field («Предприятие») is excluded from the field columns — it duplicates the synthetic column (its header cell is dropped along with the field, `visibleIndexByPosition` shifts accordingly). Boolean columns: one native `<input type="checkbox">` in a `label.report-cell__checkbox` — the SAME control in every grid and project (no custom button). A plain column is a binary toggle («Да» ⇄ «Нет»); a nullable one (`allowsNull`, the plan's `col_202`/`col_212`/`col_215`) cycles пусто → Да → Нет → пусто: the first click on an empty cell checks it, a click on «Да» goes to «Нет» (drawn as the native `indeterminate` state), and a click on «Нет» clears the value — the same result as `Delete` in a nullable cell. Number columns render through `Intl.NumberFormat("ru-RU")` (`report-cell__number`). Read-only columns are greyed (`report-cell--readonly`); calculated columns are tinted green (`report-cell--calculated`, `--cell-calculated`) — except when the row has missing components (`__missingComponents`), i.e. the code renders `<NULL>`: then the cell is tinted red (`report-cell--invalid`, `--cell-invalid`).
- **Filters.** `blockFilter` (a responsibility block from `field.responsibilityBlock`; `col_003` and `col_217` — the renovation id and the note — are always visible, `col_002` is hidden entirely; the `read_only` block is excluded from the dropdown — it only groups hidden/always-visible columns) is applied to the columns; `assetFilter` (client-side) is applied to the rows via `displaySource`. Editing constraints: `editableFieldKeys` (approver → none; everyone else → non-calc, non-read-only) and `userAssetIds` (rows the user may edit; null for admin/approver). Row creation is narrower still — only an admin or a tech-block asset worker on its assets (see «Selection payload»); the approver's row/history/clipboard actions are removed entirely.
- **Blocks.** The three responsibility blocks have **canonical display names** — `BLOCK_LABELS` in the workspace (`tech` → «1) Техническая дирекция», `ksir` → «2) Дирекция КСиР`, `mto` → «3) Дирекция МТО`). Both the «Все блоки» filter (in that order, after «Все блоки») and the level-0 column-header overlay cells (their Excel text «Блок … (раздел N)» is replaced in `overlayCells`) render these labels, so the filter and the table always agree.
- **Diff view.** A non-working version (`pendingApproval`/`archived`) is opened read-only with a diff against `diff.comparedToPlanId`: rows carry `__rowState` (`new`/`changed`/`unchanged`), changed cells are tinted, and rows deleted in the viewed version are shown as **ghosts** (`__rowState: "deleted"`, strikethrough) filled from the comparison plan by `position`. `plan.baselineBoundary` (the first row of the next baseline generation) draws a green line (`report-cell--baseline-boundary` / `report-row-header--boundary`); deletions above it are rejected by the server.
- **Clipboard.** Copy/paste are custom (capture-phase window handlers, `event.code`, `isGridTarget`, `rangeeditapply` → `beforeRangeEdit` so leases/validation/undo work uniformly), same as raw — but with **no Ctrl+X** (no cell clearing) and **Ctrl+A fully disabled**: the plan holds ~94k rows and a whole-form copy would overflow the clipboard, so the key is swallowed (revo-grid's built-in select-all included). Delete is row-level; Ctrl+Delete opens the same delete dialog as the button. The paste button is enabled when `onClipboardStateChange` reports `canPaste` — true only when the selection contains at least one editable, non-busy target cell (`cellAllowed` + `remoteLocks`/`remotePresence`, the same rule as the raw `canPasteRange`); the workspace does not override it. Select-all is swallowed even when programmatic selection leaves focus on body before React observes the range; text-editor Ctrl+A remains native.
- **Selection payload** includes `rowId` (the row the range started in) so the workspace can delete the row; row deletion uses `DeleteRecordDialog` (reused from raw). **Adding a row** is a button in the action bar (next to «Удалить строку»): it opens `AddRowDialog` with an asset `SearchAutocomplete`; on confirm the workspace calls `addRenovationRow(assetId)` (an empty row for that asset appended at the plan's end) and refreshes. **Only administrators and asset workers of the Техническая дирекция (tech) block may add rows** — other directorates' workers, block owners and approvers get `403` (`_ERR_ADD_PERMISSION`); the server enforces it, the front hides the button for those roles. The approver (a role that cannot edit the plan at all) also gets the **add/delete/undo/redo/paste** actions removed (not disabled) and their keyboard shortcuts (Ctrl+Z/Y hotkeys and the grid paste handler) are inert; copy stays. There is **no in-table placeholder row** for the renovation plan — the «Предприятие» column is read-only, edits go through the dialog. The dialog lists every asset for admins and only the user's own assets for `asset_worker` (the server enforces the same).
- **Row numbering («№»).** The row header shows the **sequential number in the current filtered scope** (`rowIndex + 1`, 1-based): after filtering the rows are numbered 1..N anew. The stored plan position (`__position`) is NOT displayed anymore — it stays only for the **baseline-boundary** line in the diff view (`baselineBoundary` is a stored position). The remote source is index-addressed by the filtered offset, so the visible number, the grid row index and the server's page offset all agree. Selection labels and presence use the same sequential numbers. The Excel export (`export.py`, column A) still writes the stored plan positions — it is a server-side full-plan document, not the on-screen view. The backend test fixture seeds rows 1-based (was 0-based via bare `enumerate`, which made the UI start at «2» on 1-based production data while tests stayed green).
- **«Перейти к строке/столбцу»** (the «№» corner’s funnel button, `RowGoToFilter`): two labelled `NumberField`s — «Номер строки» (the sequential row number in the filtered scope) and «Номер столбца». The two differ on purpose: rows re-count in the filtered scope, while **columns keep their fixed strip number** (the workbook ordinal − 1). Its bottom footer uses the shared expanding-button group with «Отменить» / «Применить» only; there is no «По умолчанию». Apply and Enter jump, while cancel, outside press and Escape close without jumping. `RenovationGridHandle.scrollToPosition(position)` scrolls to a row (`scrollToRow`, optionally centred for the reload anchor); `scrollToColumn(number)` resolves the number to the **nearest visible** column — a block filter can hide the column the user named, so the closest visible one wins (ties favour the lower number) — and scrolls via `grid.scrollToColumnProp(prop)` (retried until the horizontal window lands on it).

### Column filters in a table header

- **ONE popover for every table (`front/src/shared/ui/column-filter-popover.tsx`).** The plan, the «Сырьё»/«КППК» dictionaries and the renovation dictionaries all open the same commit-mode multi-select. What differs is only WHERE the options come from, and that is a parameter: the owner injects a `FacetSource` (`front/src/shared/ui/column-filter-facets.ts`) and gets back one `ColumnFilter` (`{column, values, includeNulls}`). The popover knows no project, no column and no API.
  - `serverFacetSource` — the plan: distinct values live in PostgreSQL (up to ~250k per column), so they page over the wire from `GET /plan/facets`. The plan wraps it in `RenovationColumnFilterPopover` (`front/src/features/renovation/renovation-column-filter.tsx`).
  - `rowFacetSource` / `computeRowFacets` — every client grid: the rows are already in memory, so the same buckets are computed there.
  - The server contract is MIRRORED on purpose (`read_plan_facets` in `back/src/renovation/service.py`): display strings, `casefold` then value ordering, NULL **and** empty string collapse into one «Пустые» bucket, `total` over the whole scope, `rowCount` over all buckets. Any change on one side must land on the other, or the two kinds of filter start behaving differently.

- **A project EXTENDS the shared popover, it never forks it.** The plan's «Идентификационный код» is the example: `col_002` is two fixed buckets («Корректные»/«Некорректные»), not a value list, and its unique-count suffix would only repeat the row count — so the renovation wrapper passes the paged source and `showUniqueCount={false}`. Selection mechanics, the master toggle, paging and the footer stay shared.

- **List and paging.** Items: «Выбрать все (N)», «Пустые» (only when the column has one), then the distinct values alphabetically. A column can hold ~248k values (`col_002` in the plan), so the list pages (`FACET_PAGE` 200, next page within 120 px of the bottom, deduped by a `Set`). The search narrows the **loaded** window only. No progress caption — new windows just appear.

- **Selection semantics.** The master stays checked while values are removed («всё, кроме некоторых»), unchecking it clears everything («Пустые» included), and unchecking the last value unchecks the master. Values a later window brings join the kept set until the user excludes something (`allStillSelectedRef`) — otherwise applying would send a whitelist missing every unloaded value. A `Separator` divides the pinned rows from the values.

- **Filter landmine.** The `NULL_KEY` sentinel enters the selection only when «Пустые» actually renders (`includeNulls && hasNulls`): react-aria keeps keys it cannot match to an item, so such a column would carry a phantom key and the master would never auto-uncheck. The applied filter normalizes `includeNulls` the same way.

- **Applying in the plan.** A filter applies when the popover closes (outside press / Escape) and rides to `GET /plan/rows` as `[{column, values, includeNulls}]`, ANDed in SQL — the row window, the «Найдено» counter and the export all respect it. Keeping every value drops the filter; keeping none selects no rows. «Сброс всех фильтров и сортировок» clears header filters with the asset/block ones. Service columns have no filter.

- **Applying in a client grid (`RawMaterialsGrid`).** The workspace owns the state: `useGridColumnFilters()` (`front/src/shared/grid/use-grid-column-filters.ts`) keeps the `Record<column, ColumnFilter>` in the URL under `?filters=` — the same key and shape as the plan — and the grid takes `filters` / `onFiltersChange`, computes the source with `visibleRows` (the shared source narrowed by the active filters, the «＋» placeholder always kept) and renders the shared popover itself.
  - Facets are counted over the rows visible under the OTHER filters, never under the column's own — otherwise its option list collapses to what it already keeps and a value could never be brought back. The plan applies the same rule server-side.
  - A column is filtered by the text its CELL shows (`facetTextOf` in `grid-config.ts`): a `displayKey` column offers its short names, a select column its labels, a checkbox «Да»/«Нет». Filtering the raw UUIDs would offer values that appear nowhere on screen.
  - RevoGrid draws its own header, so the funnels come through its API: `markFilterableColumns` gives each filterable leaf a `columnTemplate` (that is what makes RevoGrid render `.rv-filter`), and the capture-phase `beforeheaderclick` handler swallows the funnel click (it would otherwise sort the column) and opens OUR popover anchored to the header cell. `withFilterMarkers` + `updateColumns` repaint the active state. Calculated columns get no funnel.
  - Interaction with the other filters: `RowGoToFilter` numbers what the grid shows, and the sort is RevoGrid's own — both sit on top of `visibleRows`.

- **Go to row («№») — shared too (`front/src/shared/ui/row-go-to-filter.tsx`).** Any table can host it: an anchored `Popover` with two `NumberField`s (row number, column number; `rowLabel`/`columnLabel` let a form rename them). In the plan the «№» corner's funnel opens it against the fixed workbook column numbers and the filtered plan total; in a client grid the same component sits on the «№» row header (`report-row-header__filter-button`) and jumps with `scrollToRow`/`scrollToColumnIndex` over the rows the grid currently shows. Empty fields close without a jump, out-of-range rows clamp. There is **no server-side «№» range filter** (the backend still accepts `position_from`/`position_to` for compatibility; the front never sends them).

- **One funnel glyph everywhere.** Every filter affordance draws the same icon — iconoir's `Filter` — kept once as the `--filter-icon` CSS custom property (a mask, so it takes the surrounding colour) and used by the plan's overlay header, the client grids' header funnels and the «№» corner. RevoGrid paints its own three-bar `.filter-img` inside `.rv-filter` and exposes no icon option, so the built-in image is hidden and `.report-header__funnel` (the span `markFilterableColumns` puts in the header) draws the app's icon over the button's hit area. A filtered column tints it with `--accent`, the same signal the plan uses.

### Remote rows, live updates and performance

- **Remote rows (RevoGrid Pro `InfinityScrollPlugin`).** The plan holds ~306k rows, so the plugin owns a sparse source of `total` slots and fills/evicts it in chunks (`chunkSize 100`, `bufferSize 400`); the workspace only reads the scope head and supplies `loadRows(offset, limit)` → `GET /plan/rows`. A row's grid index equals its offset in the filtered plan. The config rebuilds on `[scopeKey, totalRows]`, where `scopeKey` identifies plan + asset + header filters.

- **Why the old flicker is gone.** The previous code replaced `source` on every chunk, which ran `ViewportStore.setViewport({ realCount })` and dropped `items` — the band went white. Patching the sparse source in place never resets the viewport.

- **Live updates** (edits, undo, remote cells, diff states) go through `rowPatches` → `setSourceByPhysicalIndex(store, patches, false)` + `grid.refresh("rgRow")`. The workspace mirrors the same row objects and mutates them in place, never replacing the source.

- **The mirror must be re-read on `scrollchange`** (debounced 300 ms) **and retried while empty**: the plugin does not emit `aftersourceset` for its chunks, and the first chunk arrives with no event at all — an event-only listener left `loadedRows` empty, so paste validation, undo patches and selection labels silently did nothing until a page reload. `reportLoadedRows` now returns the count and retries (150 ms backoff, ≤40) while it is 0.

- **Landmines.** (1) Unloaded slots are `{}`, not rows — every `cellProperties`/`rowHeaders`/`editableCell` access must tolerate `__id === undefined`. (2) The **initial position**: a single `scrollToRow` is often swallowed while the grid settles, so `jumpToRow` retries every 150 ms until the viewport lands within ±5 rows (≤50 attempts); the anchor is the row kept at the viewport centre (`onCenterPositionChange`, persisted per plan version), resolved onto the new scope as `anchorOffset`, with the tail jump only as a fallback; the jump is `null`ed for archives, or the working-plan position leaks into them. The **remembered row must never be overwritten by a viewport that is mid-jump**: on mount the grid shows row 1 until the restore lands, and an early `reportCenterPosition` wrote that row over the saved one (a saved 100011 came back as 12 on every reload — the reported "opens on the first row" bug). So `reportCenterPosition` returns early while `jumpInFlightRef > 0` **and** `Date.now() < restoreDeadlineRef` (a 12 s hard stop, so a jump that dies can never freeze the saved position for the session), and also skips an unscrolled viewport while a restore is still pending (`restorePendingRef`). The flag is cleared by an effect keyed on `scrollToPosition` — a bare mount-time effect ran before the jump started, left the flag stuck ON and silenced the report for the whole session (value stopped updating even on scroll). `jumpToRow` also refuses to work on a grid that has not laid itself out (`clientHeight < 3 rows` → wait and retry), and `atLimit()` must not treat a collapsed scroller as "the end": it aborts a restore on the first attempt and the viewport stays on row 1. Keep the two formulas inverse — the jump centres (`targetTop() = target*row - (h - row)/2`) and the report reads the centre — and keep the `landed()` slack symmetric: accepting a *short* jump saved that early row and drifted the position up on every open. (3) Deleted-row ghosts cannot be spliced into an index-addressed source — the diff shows them by highlighting only.
- **Remembered position in every form.** `front/src/shared/grid/scroll-position.ts` keeps where the user left each form, so a reload (or a return from another tab) reopens it there. Which forms take part is decided by the caller: `RawMaterialsGrid` accepts an optional `scrollPosition?: { form, scope? }`, and **omitting it means the form keeps no position** and opens at its own default — that is why the renovation plan does NOT use it (it has the specialised logic above: centred anchor, tail default, server-side `anchorOffset`) while every `RawMaterialsGrid` form does: «Движение», «Цены» and the dictionaries of «Сырьё», every renovation dictionary, and the КППК products/ДЗО/realization/cost/users tabs. Payload and rules: (a) the stored value is the **row id**, never an ordinal — rows are inserted/deleted between visits and sorting/filtering renumbers the visible list, so an index would silently land on another record; a missing id (deleted, or filtered out) just means "no position" and the form opens at the top. (b) The key is `reportcollector:scroll-position:<project>:<section>:<scope>` — `scope` is the filter/sorting description (`scrollScopeKey`), so a position is reused only inside the scope it was taken in: coming back with the same filters returns the same row, clearing them returns to where the user was BEFORE filtering instead of jumping somewhere arbitrary. (c) **The first visit opens at the TOP** for every form except the plan, which keeps its tail default. (d) Landmines, both already paid for once: the restore must be armed per `(form, scope)` (`lastScrollScopeRef`) — a flag cleared by a separate effect is not guaranteed to run when tabs switch, so the second form of a session never restored; and the save must listen to `viewportscroll` (`dimension === "rgRow"`) as well as `scrollchange`, because the grid does not emit `scrollchange` on every scroll — with only the latter the position simply never got written.
- **Pinned row must always be assigned.** `pinnedTopSource` is ALWAYS passed to `<revo-grid>` — `pinnedTopSource ?? EMPTY_PINNED_SOURCE` (module-level stable empty array), never a conditional spread and never a fresh `[]`. The React wrapper only writes props it receives: omitting the prop when a section has no summary left the previous section's pinned row on the element — after visiting «Предприятия» every other dictionary showed a blank pinned strip. A fresh `[]` per render is the opposite landmine: Stencil's `@Watch` fires on every reference change and reprocesses the pinned strip. The plan grid and the shared `RawMaterialsGrid` (dictionaries) both follow the always-assigned pattern; the plan's summary values come from the server aggregate over the whole filtered scope (`GET /plan/summary`), the assets tab sums its fully-loaded rows client-side.
- **Pinned summary row.** A totals band (`renovation-grid__summary-cell`) — a 36px revo-grid pinned top row — sits right under the overlay (the header levels plus the column-number strip) and follows the horizontal scroll with the header. Each additive numeric field shows the sum over the **same scope as the remote rows** (asset + header + row-number filters), fetched from `GET /plan/summary` (`read_plan_summary` → one `SUM()` per numeric column) whenever those filters change; non-numeric fields stay empty. **Non-additive fields are excluded server-side** (`_SUMMARY_EXCLUDED_FIELDS`): the defect-statement number (`col_023`), «Продолжительность, дни» (`col_026`), both «Физические объемы работ» columns (`col_083`/`col_084`) and the whole «Статус готовности МТР к проведению ремонта» block (`col_208`–`col_211`, `col_214`) — their summary cells stay empty. Every cell keeps all four borders (the row reads as a bordered strip); a non-empty total is tinted like the calculated columns (`--cell-calculated`). The totals are the stored values, so they match what the grid shows.
- **«Предприятия» dictionary.** The descriptors (`grid-config.ts` → `renovationAssets`) put **«Число ремонтных работ»** (`repairCount`, computed server-side — the working plan's row count per asset) right before «Стоимость итого, руб. без НДС» (`totalCost`, the sum of `col_031`). Both are fixed/calculated columns and both are exported (the server's assets `ALLOWED_KEYS` mirrors them). The tab's pinned totals row sums both.

### Data semantics and undo/redo

- **The «Идентификационный код» filter is two buckets, not a value list.** A value list of mostly-unique codes would be unusable, so `col_003` offers exactly «Корректные»/«Некорректные» (`GET /plan/facets?column=col_003` returns those two, `hasNulls=false`). With the renovation-ID generator **off** (`RENOVATION_ID_FORMULA_ENABLED` in `back/src/renovation/renovation_id.py`) a code is judged by uniqueness alone: «Некорректные» are the codes that appear **more than once inside the plan**, plus the empty ones — exactly what blocks submit. The condition is evaluated in SQL (`_renovation_id_is_correct_condition(plan_id)`, a correlated `GROUP BY … HAVING count(*) > 1` subquery scoped to the plan), so it filters the window and the export without loading the Python side.
- **Undo/redo** mirror raw: `pendingCommitRef` race guard, `skipActionId`-based conflict resolution, counters refreshed from `getUndoState()` on version switch, Ctrl+Z/Ctrl+Shift+Z/Y by `event.code`.

- **Lifecycle.** `submit` (working → pendingApproval; admin or any block owner) and `approve` (pendingApproval → archived + a new working copy with `baseline_generation + 1`; admin or approver) both reset the undo counters. `submit` first drops empty drafts, then refuses with `409` while any remaining row's work ID (`col_003`) is **empty or duplicated** — the message names the counts and the first offending rows, and the front shows it in a `SubmitBlockedDialog` instead of a toast. A defect number dropped leading zero is restored when the id is built (`706179` → `0706179`), otherwise the 7-digit rule would reject every short number.

- **Export.** One action in the action bar (`createRenovationExportJob` → native download of the job file). The backend runs it as a **background job** (see `docs/ARCHITECTURE.md`, «Renovation plan export jobs») and the endpoint **streams the growing file**, so the browser's own download UI shows progress for the whole generation while nothing is buffered in page memory. Closing the tab cancels neither the job nor the download. The worker streams rows through a server cursor and writes the workbook incrementally; column letters and formula templates compile once per export.

- **Export file name** follows the other forms: `Пообъектный план — {рабочая версия | версия на согласовании | утверждённая версия} (дд.мм.гггг, чч.мм.сс).xlsx`. The timestamp is the version's freeze moment — the plan `updated_at` for a pending/archived version, the **latest row edit** for the working one. The name goes out RFC 5987 (`filename*=UTF-8''…`) so the Cyrillic survives.

- **«Скачать видимую таблицу»** applies both filters **server-side**: rows narrowed to the asset, columns trimmed to the selected responsibility block (plus the always-visible `col_002`, `col_003`, `col_217`), the surviving columns compacted and the merged header ranges re-clipped. With no filter the sheet keeps the full 218-column layout minus the hidden `col_218`. **Calculated columns are recomputed at export** (`formula_engine().materialize`), so derived fields are present even when the stored cell is NULL — an imported row may never have run the on-edit recalculation. Every header cell of a merged range carries the bordered style so Excel draws the full frame.
- **Collab** is enabled only for the working version: room key = project, section = `renovationPlan`, `reportMonth = null`, `onRowsChanged` → refetch, remote cell values patched into the **loaded rows** only when not archived (the remote source holds only a window, so a value for an unloaded row is picked up when its chunk loads). The patch covers **calculated** fields too (formula results): the backend publishes them as `cell:changed`, and the workspace applies them to the mirrored row objects. `col_003` is a plain editable cell now (the ID generator is off), so it syncs like any other typed value — no derived-value special case. Presence/leases/tooltips use the same `remoteLocks`/`remotePresence`/`remoteCellInfo` maps — now the shared `useRemoteCellMaps` hook (`front/src/shared/collab/use-remote-cell-maps.ts`), content-stabilized so a presence heartbeat with unchanged state doesn't rebuild the columns memo — and the same preemption/`suppressSelectionSendRef` pattern as raw.
- **CSS** lives in `globals.css` under a `.renovation-grid` block (theme vars, cell borders, state tints, overlay, baseline line) — the raw-materials rules are scoped to `.raw-materials-grid`, so the renovation grid gets its own copy. Keep `.dark .renovation-grid { color-scheme: dark }` if the `theme` prop changes. **Header cells paint only LEFT+BOTTOM lines** (the container paints the single top line, and each cell above paints the shared bottom edge) — a TOP line on every cell doubles the borders between the level-0 block row and what's below into 2px.
- **Pinned mode: the `min-height: 300px` landmine.** The revo-grid library stylesheet sets `revo-grid { min-height: 300px }` (a Safari stretch workaround). Under the pinned 288px overlay (11 levels + the column-number strip) the data viewport is often shorter than 300px — the grid then refuses to shrink, overflows the clipped `.grid-viewport` and the trailing rows become unreachable while the footer still shows below. `.renovation-grid { min-height: 0 }` in globals.css beats the host rule — don't remove it. (Fullscreen "fixes" it only because the toolbar/footer collapse and the viewport clears 300px.)
- **Perf: the presence echo loop.** The grid's selection effect depends on `onSelectionChange`, which the workspace recreates whenever `room` changes; `room` changes on every presence echo (the server broadcasts the sender's own update back). With a selection, each cycle sent a fresh content-equal object → `setSelection` re-rendered the whole workspace + grid → new send → … a self-sustaining loop at WebSocket-RTT speed (measured: 31 presence sends per 1.5 s idle, 61 → 20 fps horizontal scroll, button animations janking). The workspace's `handleSelectionChange` drops content-equal payloads (`lastSelectionContentRef`); without a selection `setSelection(null)` bails out, which is why the loop only existed while a cell was selected. Don't remove the guard, and keep any new selection-callback out of effect deps or guard it the same way.
- **Placeholder add-row selection.** Focusing a cell (or selecting the «+» row) of the trailing `isPlaceholder` record-creation row does **not** emit a selection: the grid's debounced selection effect detects that every covered row is a placeholder and reports `{ label: null, cellKeys: [] }` — so nothing appears in the footer «Выделено» and nothing is broadcast over presence (a creation row has no persistence keys and never blocks anyone).
- **Dictionary export allow-lists.** Each export validates that every requested column key is in the server's per-section `ALLOWED_KEYS` (raw `src/raw_materials/export.py`, renovation `src/renovation/export.py`). A column missing from the list fails the export with «Экспорт содержит скрытый или недоступный столбец.» The **users** tables export with their real on-screen columns: raw users include `lastAuthenticatedAt`, renovation users include `role`, `block`, `lastAuthenticatedAt` (the enum codes are written as their keys); the renovation **assets** section exports its computed `repairCount`/`totalCost` columns too. Keep those key lists in sync with the grid descriptors (e.g. `grid-config.ts`) or the export breaks again.


## КППК (`front/src/features/kppk/`)

The three dictionary tabs («Продуктовые позиции», «Сырьевые позиции», «ДЗО») reuse `RawMaterialsGrid` and the shared `ActionBar`; the descriptors (`kppkPositions`, `kppkRaws`, `kppkOrgs`) live in `grid-config.ts`. There is no collaboration room — but the shared action-bar mechanics are wired in:

- **Action bar order:** copy, paste, undo, redo, export, delete.
- **Undo/redo** — the shared server-side journal, scoped per tab: every mutation carries the page-lifetime `session_id` (`getCollabSessionId`), and the state is re-read from `GET /api/kppk/undo-state?section=&session_id=` after every commit and after every undo/redo attempt (never local ±1 arithmetic). Ctrl+Z/Ctrl+Y match on `event.code`; `runUndo`/`runRedo` await the in-flight PATCH first (`pendingWriteRef`), so an immediate Ctrl+Z after Enter undoes the edit just made; a conflict stores `pendingSkip` and the second press passes `skipActionId`. Nothing is published over WS, so an applied undo/redo refreshes the grid itself. `KppkSection` is keyed by tab — switching tabs remounts it and each tab re-reads its own state. Undo/redo are admin-only (the buttons render only for admins; the server enforces it), the state read is open to every member.
- **Export** — the shared «Скачать в Excel» dropdown («Скачать всю таблицу» / «Скачать видимую таблицу») lives in the BOTTOM action bar and nowhere else: `ViewStrip` no longer renders an export button at all (it takes no export props), so no form can duplicate it. `exportKppkTable` (`front/src/shared/api/kppk.ts`) POSTs `{section, columns, rowIds, fileName}` to `/api/kppk/export` and downloads the XLSX as a blob (`downloadBlob`) — a native link cannot carry the authorized POST. Column keys come from the grid (`getExportState`), validated against the server-side per-section allow-list (`back/src/kppk/export.py`); widths go through `pixelsToExcelWidth` (clamped 8..60). Available to every project member, like the reads — «Пользователи» included (the list is readable by members, so its export is too).
- **The export button is disabled over an empty table, in every project.** The row count the action bar gets is the one the footer status shows: the grid measures it (`onViewStatsChange` → `filteredRows`, placeholders and deleted rows dropped) and the section republishes it with its export state. Do not count the section's own pre-render list instead — the two numbers drift apart (the status says «N строк» while the button stays disabled). `buildExportAction` (and the view strip's own button) disable on `rowCount === 0` and explain «Нечего выгружать: таблица пуста.» on hover.

### «Продуктовые позиции»

- **Two views over the same stored positions** (`kppk_org_products`: one row per product × ДЗО; the grouped descriptors are `kppkPositions`). The tab owns a «Настройка акциза» checkbox in the Tabs row (`kppk-workspace.tsx`), unchecked by default:
    - **default — grouped** (`GET /product-positions?view=grouped`, `KPPK_GROUPED_POSITION_DESCRIPTORS`): the historical look. One row per PRODUCT (unnumbered last, then name), the product typed once and its ДЗО set multi-selected in a single `assetsMulti` («ДЗО») cell. The `orgNames` cell write diffs the set (`replace_org_links`): added assets become new positions, removed ones drop theirs, and the surviving pairs keep their «Заполняемый акциз» flag. A product with the same name adds positions to it (no duplicate product); the placeholder needs only a product name — its ДЗО set may be empty and filled in later. Products with no position at all still appear, with an empty ДЗО set — the dictionary knows they exist, and their own cells («№», «Наименование») stay editable (the row id is then the PRODUCT id);
    - **«Настройка акциза»** (`?view=positions`, `KPPK_POSITION_DESCRIPTORS`): one row per POSITION, where `has_excise` is set per product × ДЗО. The «№» and «Продукт» columns are PRODUCT cells — only the run's head row carries them and `CellMergePlugin` merges them over the run, so a product listed at three assets reads as one block with three asset lines. «ДЗО» is a single-select reference cell, «Заполняемый акциз» a boolean position cell; adding a row = adding a POSITION (the placeholder needs both a product and a ДЗО), and deleting one removes the position, taking the product with the last of its positions. A product created without assets gets them later from the grouped view. A sort un-merges the blocks, clearing it restores them;
    - both views write the same records (a grouped create posts the whole `orgNames` list, deduplicated); the Excel export always uses the POSITION shape so every pair is spelled out;

### «Реализация» and «Себестоимость»

- **«Реализация»** (`kppk-realization-section.tsx`) — one slice × ДЗО × period, read-only except for admins:
  - **the grid is always there** — a period with no source data is not an empty state: `just seed-kppk` rebuilds one row per (ДЗО × product of the «Продуктовые позиции» matrix × market) and one per (ДЗО × product) for «Себестоимость» for every month from September 2023 to December of the next year, all numeric cells left empty, so the form is the place where the data is ENTERED, not just read. Rows are real records (uuid + natural keys of the copies), which keeps PATCH, undo and the collaboration room working unchanged; there is no virtual/zero-filled read-time row anywhere. The rebuild truncates these tables first (the seed owns them), so a product removed from the matrix cannot leave a stale period behind;
  - **the excise is a product-level figure**, not per market: the copies still carry the column on every market row (no key change — `kppk_realization_plan` / `kppk_realization` have no unique constraint besides the uuid PK), but every row of a product holds the same value (migration `0016_kppk_excise_per_product` collapsed the old per-market copies, largest non-zero value wins). Volume and excise are NULLABLE, like every source figure (`0023_kppk_nullable_volume_excise`): an empty cell means "not filled", and a cleared cell is stored as NULL instead of a measured zero. «Акциз» is shown for every asset that levies an excise on at least one product (no toggle any more) and is a **merged column**: its `MergeData` range covers the same product block as «№»/«Продукция», every covered row renders an empty cell, and the block's rows all subscribe to ONE canonical key (the block lead's) so a live edit from any user paints all of them. An edit is fanned out to the whole block on commit (`expandExcise` in `kppk-excise.ts`) — otherwise the hidden rows keep the old rate and sorting (which un-merges) exposes the disagreement;
  - **the excise is SCOPED**, and the scope is the product POSITION (migration `0018_kppk_excise_on_position` moved it off the ДЗО): «Продуктовые позиции» is one row per **product × ДЗО**, and `kppk_org_products.has_excise` — «Заполняемый акциз» — is a per-position column of that tab. An asset whose positions are all unflagged returns an empty `exciseProducts` — the «Акциз» column is dropped from the grid entirely (`visibleDescriptors`), so switching to an asset without an excise hides it. On a flagged asset only the flagged products get an editable excise cell; the rest render a `null` cell whose rows carry `lockedCells: [exciseKey]` — a generic `GridRow` flag the shared grid honours in `isCellReadOnly` **and** `canEditDescriptor`, so no editor opens and a range paste skips the cell (the section also skips its canonical key, and `expandExcise` drops such an edit). The user therefore never reaches the server rejection; `_check_excise_scope` (`400 «…акциз не предусмотрен»`) stays as the server-side backstop, while clearing a wrongly entered rate is still allowed;
  - the leading fixed columns are «Продукция» + «Рынок сбыта» (the «№» column was removed from both «Реализация» and «Себестоимость» — the number is still the server's sort key, it is just not shown); the server sorts by the product NUMBER (unknown names last, alphabetically), markets in the market order, so rows of one product stay together;
  - `CellMergePlugin` folds each product's runs over the leading «Продукция» leaf (`column: 0`), so the name is one tall cell;
  - header sorting is enabled. With no custom sorting, the server order (product number → market) is shown with a merged product-name cell. When a custom sort is active, `RawMaterialsGrid` clears `cellMerge` and the section repeats the product name on every row; clearing the sort restores the grouped values and merge plugin;
  - export replays the toolbar selection: `POST /api/kppk/realization/export` with `{slice, orgId, month, year, columns, fileName}` re-reads the same ordered view server-side (`back/src/kppk/realization.py`), so «вся» and «видимая» are the same table here. The workbook repeats the grid's merged product block: `TableWorkbookWriter(merge_rows_by=…)` merges consecutive data rows whose values in ALL the listed columns are equal, each of those columns in its own range, and the run survives batching (`write_rows` is called per chunk). The keys are **schema / `model_dump()`** keys, not export column keys — `("productNum", "product")` here, a harmless superset since the «№» column is no longer exported; a wrong key silently matches nothing and the column stays unmerged. Only the columns actually exported are merged, empty cells never merge, and a one-row run is not a merge. The header's own merges (from `headerPath`) are separate and unaffected.
