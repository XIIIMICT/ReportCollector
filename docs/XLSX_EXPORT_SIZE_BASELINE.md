# XLSX export size — Phase 0/1 baseline

Scope: reconnaissance and a reproducible, database-free baseline only. **No
exporter code, dependency, lockfile, frontend, job topology or production data
was changed.** Machine-readable evidence:
`docs/XLSX_EXPORT_SIZE_BASELINE.json`. Harness:
`back/tests/benchmark_xlsx_export_size.py`; harness-correctness tests:
`back/tests/test_benchmark_xlsx_export_size.py`.

All workload numbers below are **synthetic approximations** generated by the
harness on the disposable local CI stand. The only real-production figures
quoted here come from the incident documented in `docs/DATA-JOBS.md`: a plan of
about 306k rows whose **uncompressed** `xl/worksheets/sheet1.xml` was about
3.3 GiB, while the final compressed XLSX download was about 520 MB. The 3.3 GiB
is a ZIP entry size, not the final file size; neither figure was measured by
this work. No sanitized production workbook exists in the repository, and the
`docs/samples` sample is `.xlsb` (an import template, not an export).

Two writers only, both on `src/common/xlsx_stream.py` mechanics:

- `RenovationWorkbookWriter` (`src/renovation/export.py`) — plan-specific layout.
- `TableWorkbookWriter` (`src/common/xlsx_table.py`) — every grid/dictionary.

## 2. Library, compression and memory boundaries

- **openpyxl 3.1.5** is pinned in `back/uv.lock` and installed in the
  `back/.venv`. It is **not** the writer: it supplies
  `get_column_letter`/`range_boundaries` to the exporters and `load_workbook`
  to the validation tests. The XLSX is emitted as hand-built OOXML strings.
- `pyxlsb 1.0.10` is import-only. `zlib 1.3.1.zlib-ng`, Python 3.15.0
  (MSC v.1951, 64-bit AMD64), Windows 11 build 10.0.26300.
- Both writers open `zipfile.ZipFile(..., "w", compression=ZIP_DEFLATED,
  compresslevel=1)` over `xlsx_stream.UnseekableSink`: append-only entries
  with data descriptors, plain ZIP (no zip64). `xlsx_stream` raises
  `zipfile.ZIP64_LIMIT` to `(1<<32)-1` on import; measured in-process value
  4294967295. Level 1 is therefore already the baseline, not an untried knob.
- Strings are always **inline** (`t="inlineStr"`); there is no
  `xl/sharedStrings.xml` part and no switch in either writer.
- Streaming/materialization: DB rows are streamed with server-side cursors in
  jobs (`iter_plan_export_rows`, `TableSource.batches`, 500 rows); the inline
  renovation-plan endpoint materializes its row list; worksheet rows are
  written in batches (500 rows in the plan/query paths, 5000 in the generic
  table-job path), one `<row>` string at a time; ZIP output is streamed
  append-only to a queue sink or a `.part` file. Only the static package parts
  and the plan layout (217 columns × 11 header levels, 475 merges) are built
  eagerly. `close()` enforces the promised row count before finalizing.
- `UnseekableSink` is why the file can be tailed while growing; any change to
  compression metadata, zip64 or seekability breaks the download contract.

## 3. Workbook features exercised by tests / variants

- Plan (`test_renovation_export_format.py`): ascending `<row r>` with the
  totals band written before data (rows 1–13 then 14+), unique merge refs,
  exact `SUM(first:last)` with cached value, cached-only totals without a row
  count, row-count mismatch failure, data-descriptor ZIP headers, 4 GiB
  `ExportTooLargeError` path.
- Table (`test_xlsx_table_merges.py`, `test_export.py`): multi-level
  `headerPath` merges, vertical run merges across batch boundaries, empty runs
  not merged, alignments, frozen pane, borders, column widths, `dimension`
  `A1:B4`, datetime/number formats, live deviation formulas, pinned `SUM`
  totals, hidden `Списки` sheet with list validations.
- `valuesOnly` is a real product switch: `true` writes stored numbers (default
  in the UI), `false` restores live formulas (133 plan formula columns at full
  width; table deviation columns and pinned totals).
- Also present but **not exercised by the new harness**: KPPK operator dumps,
  real filters/sorting/asset scoping, snapshots, Hyperlinks/conditional
  formatting/print settings (the writers emit none of these), and the
  background worker/HTTP transport.

## 6. OPC / XML inspection

- `xl/worksheets/sheet1.xml` is 95.7% of the plan package at 20 rows, 99.86%
  at 1k rows and 99.99% at 10k rows (18,332,149 of 18,333,842 compressed
  bytes). Sheet parts are ~98.4% of ZIP part bytes (~97.6% of the final file)
  at 1k table rows; tiny tables are dominated by fixed package parts instead.
- Part inventory is minimal: `[Content_Types].xml`, `_rels/.rels`,
  `xl/workbook.xml`, `xl/_rels/workbook.xml.rels`, `xl/styles.xml`, worksheets.
  **No** `sharedStrings.xml`, theme, media, drawings, comments, pivot caches,
  external links or embedded objects are emitted, so there is nothing in those
  categories to remove.
- Styles: plan `cellXfs=10` (1,956 B uncompressed / 674 B compressed); table
  `cellXfs=22` (4,003 B / 753 B) — 10 base styles plus 12 bounded alignment
  variants, deduplicated by `(base, horizontal, vertical)`. 2 **exact**
  duplicate xfs (ids 6 and 7 in the shared catalogue) are present in both
  writers, contributing only a few hundred bytes; no per-row style growth.
- Strings: inline only; no shared-string table to tune. Unique-long fixtures
  have 9.14 M inline text characters at 2k rows and a worse compression ratio
  is not observed — the ratio actually *improves* (8.57 vs 4.83) because
  unique strings raise uncompressed bytes much more than compressed bytes;
  the final file is still 3,845,273 B vs 3,646,641 B for the repeated-text
  fixture (+5.4%).
- Cell semantics at 1k plan rows: 219,821 serialized `<c>`, 217,565 with a
  value, 2,256 empty `<c s="…"/>` **all in the 13 header/aggregate rows**;
  exactly 0 bare empty cells. The empty-cell count is constant across 20,
  1,000 and 10,000 rows — it is not a row-driven growth mechanism. In the
  sparse table fixture the opposite holds: 14,009 of 22,022 cells are styled
  empties in data rows, because `TableWorkbookWriter` writes a bordered
  placeholder for every `None` (a visual contract, not inert bytes).
- `<dimension>`: table writer emits it (`A1:K2002`) and it is **not** inflated
  (matches the actual last row/column in every workload). Plan writer emits
  **no** `<dimension>`: a direct `load_workbook(..., read_only=True)` check on
  the generated 1k-row plan reports `max_row=None`, `max_column=None`, while
  normal mode reports `1013 × 217`. This is a pre-existing baseline gap noted
  in `back/AGENTS.md`; no exporter change was made in this phase.
- Merge ranges: 475 fixed header/band merges in the full plan, 37 in the
  block-filtered plan, 109–209 in the table fixtures (including vertical data
  runs). The merge block is 12,967 B uncompressed / part of the 12,991 B tail
  in the full plan — fixed overhead, independent of row count.
- Value kinds at 1k plan rows (values): 176,001 numeric serials, 41,564 inline
  strings, 2,256 styled empties. In formula mode: 133,001 formulas (with
  cached numeric values), 43,000 numbers, 41,564 strings.

Ranked conclusion for the dominant workload (full plan): **the per-cell XML

"generic XLSX tip": each is measured against these writers' actual output.

## 7. Hypotheses carried into Phase 2 (not tested, not implemented)

1. Shorter cell references cannot help without changing the 217-column layout
   (contract); the wrapper bytes are mostly `r="XX14"` + `s="N"` that Excel
   needs. Measure before touching.
2. Style dedup has a measurable but negligible ceiling (~2 xfs, <1 KB).
3. Switching string storage to shared strings is not exposed by either writer;
   inline-string values are only ~24–40% of uncompressed sheet bytes, so a
   post-processing rewrite is unlikely to pay for its complexity/compatibility
   risk. Unmeasured — do not claim a result.
4. Stronger ZIP levels are unmeasured; the writers already use level 1. Any
   experiment must preserve data-descriptor entries and OPC relationships.
5. Adding a plan `<dimension>` is a correctness fix candidate, not a size win
   (it adds bytes). It is explicitly out of Phase 0+1 scope.

# Phases 2–5 — experiments, implementation and validation (2026-11-27)

Everything below was measured on the same deterministic fixtures, in the same
environment and with the same harness as the Phase 1 baseline. Machine-readable
evidence: `docs/XLSX_EXPORT_SIZE_COMPRESSION.json` (baseline commit
`f0340c3bfa3ea20f036cbeb814759eae4d7ae4aa`) and
`docs/XLSX_EXPORT_SIZE_OPTIMIZED.json` (implementation commit
`e1c6c9db467a35ff47d913df50f757b8901f6f38`). The implementation changed exactly

## Phase 2 — hypotheses and controlled experiments

The Phase 1 byte profile established the ranking that drove the experiments:
per-cell XML wrappers are the largest uncompressed contributor (5,259,376 B at
1k plan rows), value/formula content is second (3,517,425 B; 7,321,017 B with
formulas), and fixed header/merge/style overhead is <2% of compressed bytes.
Only candidates that could act on those contributors were tested.

### H1 — ZIP deflate level (ACCEPTED, implemented)

Mechanism: both writers opened each entry with `ZIP_DEFLATED, compresslevel=1`.
The same OOXML part bytes were recompressed at other supported levels over
`UnseekableSink`, so the only variable was the compressor. The harness exposes
this as `python -m tests.benchmark_xlsx_export_size compression --levels …`;
it verifies byte-for-byte equality of every entry name/order/part against the
level-1 render before recording a result. Level 1 recompression is within
0.16% of the real level-1 writer (one-shot `writestr` vs streamed deflate
choose slightly different match blocks), a control noise floor far below the
observed deltas.

A 5-rep intermediate sweep (`--levels 1 3 4 6 9 --out NUL`) showed the shape of
the trade-off: plan_large 18,334,632 → 12,878,178 (L3, −29.8%) → 12,432,083
(L4, −32.2%) → 11,607,410 (L6, −36.7%) → 10,582,447 (L9, −42.3%) bytes, with
compression time 0.296 → 0.368 → 0.483 → 0.762 → 2.098 s; table_large
1,125,418 → 756,469 (L3, −32.8%) → 689,001 (L4, −38.8%) → 644,995 (L6,
−42.7%) → 595,956 (L9, −47.1%) bytes, 0.021 → 0.025 → 0.029 → 0.042 → 0.101 s.
Level 6 captures nearly all of the win at ~2× compression CPU; level 9 costs
3–7× CPU for a further 4–7 percentage points. Every level preserved the
data-descriptor flag (bit 3) and the plain-ZIP header (no zip64 extra,
`extract_version < 45`) on all entries.

Harness landmine found while building the experiment: on Python 3.15,
`ZipFile.open()` copies `compresslevel` only when it creates a **new** `ZipInfo`.
An explicitly supplied `ZipInfo` keeps its own `compress_level` (default
`None` → zlib level 6), silently ignoring the `ZipFile` setting. The experiment
therefore sets `fresh.compress_level = level` per entry. The production writers
pass entry names as strings and are unaffected.

### H2 — styled-empty cells (REJECTED: semantically required)

The sparse table fixture contains 14,009 empty `<c/>` cells in data rows.
Parsing their styles against `xl/styles.xml` shows styles 1, 8, 13, 16 and 19,
**all** with `borderId="1"` (thin border); the plan's 2,256 empties are style 1
in header/aggregate rows, also bordered. There are **zero** style-0 empty
cells. The blanks are the border/fill contract for the grid, not inert bytes,
so none can be removed. Pinned by `test_every_styled_empty_cell_carries_a_border`.

### H3 — cell XML wrappers / default style attributes (REJECTED: already optimal)

Verified that all five cell builders (`text_cell_xml`, `number_cell_xml`,
`styled_cell_xml`, `formula_cell_xml`, `bool_cell_xml`) omit the `s` attribute
when style is 0; generated plan and table sheets contain zero `s="0"`
attributes. The remaining wrapper bytes are `r="…"` refs and `s="N"` for
non-default styles, which Excel needs and which follow from the contracted
217-column layout. Dropping refs, rewriting XML after the fact, or changing
the layout would be fragile or a behavior change; no tested safe reduction
exists. Pinned by `test_default_style_attribute_is_already_omitted`.

### H4 — shared strings vs inline strings (REJECTED: no supported switch)

Neither writer exposes a string-storage switch and neither emits
`xl/sharedStrings.xml`; a post-processing rewrite was explicitly not attempted.
Measured trade-off context: the 1k plan has 41,564 inline strings / 468,350
characters, and the 2k unique-long fixture has 9.14 M characters yet a *better*
compression ratio (8.57 vs 4.83 for repeated text) — the existing deflate pass
already exploits repeated prefixes. A shared-string table would add `<si>`
wrappers and per-cell `t="s"` references while requiring every unique string
to be resident in Python memory, conflicting with the bounded streaming design
on ~300k-row exports. With H1 accepted, the expected gain does not justify the
memory/compatibility risk.

### H5 — formula-enabled variant (CONFIRMED contract-required, not removed)

The plan 1k formula variant contains 133,001 `<f>` elements whose serialized
bytes total **3,803,613**, exactly the uncompressed sheet delta
(12,702,977 − 8,899,364). The +73.9% is therefore real formula payload plus
its compression behavior, not stray wrappers. `valuesOnly=False` is a documented
product switch and Excel evaluates the formulas (see Phase 4), so they stay.

## Phase 3 — implemented change

- `back/src/common/xlsx_stream.py`: new documented `ZIP_COMPRESSLEVEL = 6`,
  replacing the two hard-coded level-1 settings.
- `back/src/common/xlsx_table.py` and `back/src/renovation/export.py`: optional
  keyword-only `compresslevel` on both writer constructors, defaulting to the
  shared constant; the level is passed only to `ZipFile`, so the worksheet XML,
  package parts, streaming sink and append-only data descriptors are unchanged.
- `back/tests/benchmark_xlsx_export_size.py`: reusable `compression` experiment
  mode, explicit level override in `render()`, and dynamic compression metadata
  in the evidence environment.
- `back/tests/test_xlsx_export_size_optimizations.py`: 9 regression tests for
  the level, configurability, ZIP contract, semantic equivalence, styled blanks,
  omitted default styles and formula payload.

## Remaining limitations and out-of-scope items

- All workloads are deterministic synthetic approximations; the real ~306k-row
  plan (~3.3 GiB **uncompressed worksheet**, ~520 MB final XLSX) was **not**
  re-measured end to end after the level-6 change. Linear extrapolation from
  the 90 MB-uncompressed fixture puts compression CPU at roughly 36 s (L1) vs
  90 s (L6) for a 3.3 GiB sheet — an estimate, not a measurement — while DB
  streaming still dominates a real export's wall time.

## Target-host full-scale gate (OPEN)

The synthetic matrix proves the byte reduction on identical OPC parts; it does
not prove that a real 306k-row export can be generated, served and opened
after changing the Deflate level. This gate stays OPEN. A maintainer with a
disposable staging environment and representative seeded data should:

1. Seed a disposable plan with ~306k rows (never production data) and record
   row count, schema, commit SHA, Python/zlib versions, OS, available memory
   and disk.
2. Start a real plan export job and download it through
   `GET /api/renovation/plan/export/jobs/{id}/file` while the `.part` file is
   still growing; use `E2E_TEST_PASSWORD` and the reserved `.test` identity.
3. Record export duration, peak RSS/working set, disk high-water mark, final
   XLSX bytes and the uncompressed size of `xl/worksheets/sheet1.xml` via
   `ZipInfo.file_size`. Confirm that entry remains below the plain-ZIP
   ceiling (`4 GiB - 1`); do not switch to streaming ZIP64 without new Excel
   compatibility evidence.
4. Run `zipfile.testzip()`, assert the worksheet row count and representative
   values/formulas, verify `.part` → final-file publication happened exactly
   once, and open the workbook in Microsoft Excel or LibreOffice on the target
   host. LibreOffice is not installed on the local Windows host; Excel COM was
   used only for the small synthetic workbooks.
5. Keep the reproducible synthetic harness command available for regression:
   `uv run --directory back python -m tests.benchmark_rollout_workload --rows 306000 --reps 5 --import-rows 10000 --commit <sha>`.
   That harness seeds data and measures windows/facets/exports; it does NOT by
   itself exercise the full-size worker + growing-file download path.

No arbitrary row/file limits were added to make this gate pass. Level 6 stays
accepted until real-scale evidence shows an unacceptable CPU, memory, disk or
latency regression.
- Wall-clock time is noisy across sessions (an earlier identical matrix run was
  slower); only the byte deltas are exact.
- The pre-existing missing plan `<dimension>` (Phase 1 §6) is a read-only-mode
  correctness gap, not a size win; it stays out of this change.
- No optional CSV+gzip or Parquet format was implemented — replacing XLSX is
  explicitly out of scope. No row/cell/size/time limits, post-processing
  rewrites, dependency changes or infrastructure changes were introduced.
