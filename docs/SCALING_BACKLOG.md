# Масштабирование и надёжность: что осталось сделать

Рабочий документ. Заведён после настройки наблюдаемости (метрики, дашборды, алерты) —
наблюдаемость **показывает** предел, но не снимает его. Здесь — то, что нужно
сделать, чтобы система выдержала сотни пользователей и постоянное совместное
редактирование.

Порядок = приоритет. Пункты со статусом **НУЖЕН ВНЕШНИЙ РЕСУРС** не сделаны и не
могут быть сделаны без вас (доступ, решение, инфраструктура).

## 1. Нагрузочные тесты — их нет вообще

**Почему первым.** Любой порог (latency, число соединений, размер пула БД),
выбранный без базовой линии, — это догадка. Сейчас мы знаем только, что при
3 соединениях p95 ≈ 230 мс. Что будет при 50 — неизвестно.

**Что нужно:**
- сценарий HTTP: чтение грида «Движение» (~94k строк), «Реализация» КППК за месяц,
  экспорт Excel; разными N (1, 10, 50, 100 параллельных).
- сценарий WS: N клиентов в одной комнате, каждый шлёт правки ячейки; замер —
  сколько событий доходит, сколько клиентов отбрасывается по `ws_slow_consumers_total`.
- Инструмент: `locust` (Python, уже есть uv) или `k6`. Для WS `locust` удобнее.
- **Выход:** числа, на которых строятся пороги алертов и принимаются решения по §2–§4.

**Статус:** не начато.

## 2. Доставка алертов по почте — **СДЕЛАНО (2026-10-27)**

**Что работает.** Правила (`infra/prometheus/alert-rules.yml`) срабатывают,
Prometheus отправляет в Alertmanager, Alertmanager группирует и **отправляет
письмо**. Проверено вживую: тестовый алерт → `level=DEBUG source=notify.go:876
msg="Notify success" component=dispatcher receiver=support-mail integration=email[0]
… duration=1.07s`, письмо пришло на `SUPPORT_MAIL`.

**Почему не работало раньше — две причины, обе НЕ про сеть:**

1. **Порт 465 вместо 587.** `smtp.mail.ru:465` — это *implicit TLS*: сервер сразу
   ждёт TLS-рукопожатие. Alertmanager с `smtp_require_tls: true` (по умолчанию)
   начинает с обычного `EHLO` и ждёт **STARTTLS**, которого 465 не объявляет:
   `'require_tls' is true (default) but "smtp.mail.ru:465" does not advertise the
   STARTTLS extension`. Порт **587** объявляет `250 STARTTLS` — он и нужен.
   (Диагноз «порты закрыты» в старой версии этого пункта был верен на тот момент,
   но к моменту починки сеть уже открылась, и осталась именно эта ошибка.)
2. **Неверный `ALERT_SMTP_USER`.** В нём стоял ящик-**получатель**
   (`s.scorpi-on@ya.ru`), а пароль приложения и `FROM` — от ящика-**отправителя**
   (`streetjoy@mail.ru`). mail.ru отвечает на это
   `535 5.7.0 NEOBHODIM parol prilozheniya / Application password is REQUIRED` —
   сообщение выглядит как «нужен пароль приложения», хотя дело было в том, что
   логинились НЕ тем ящиком. Проверено всеми способами (`login()` в двух режимах,
   raw `AUTH PLAIN`, `SMTP_SSL` на 465) — отказ одинаковый, пока не совпали
   USER/FROM/PASSWORD.

**Правильная конфигурация** (`.env`, не в репозитории):

```
ALERT_SMTP_SMARTHOST=smtp.mail.ru:587
ALERT_SMTP_USER=streetjoy@mail.ru      # тот же ящик, что FROM
ALERT_SMTP_FROM=streetjoy@mail.ru
ALERT_SMTP_PASSWORD=<пароль приложения mail.ru, 16 символов>
SUPPORT_MAIL=s.scorpi-on@ya.ru         # получатель
```

`ALERT_SMTP_USER` и `ALERT_SMTP_FROM` **обязаны быть одним ящиком**: mail.ru
отклонит отправку от чужого адреса, даже если логин верный.

**Пароль приложения обязателен** — обычный пароль аккаунта mail.ru для SMTP не
принимается (`NEOBHODIM parol prilozheniya`). Выдаётся на
https://help.mail.ru/mail/security/protection/external; при отзыве старый
мгновенно перестаёт работать.

**После изменения `.env`** нужен `just monitoring` (или
`docker compose --profile standalone up -d --force-recreate alertmanager`):
`entrypoint.sh` подставляет значения в `/tmp/alertmanager.yml` при СТАРТЕ
контейнера, Alertmanager переменные окружения в `to`/`smarthost` сам не
раскрывает.

**Проверка доставки:**

```bash
curl -X POST http://localhost:9093/api/v2/alerts -H 'Content-Type: application/json' \
  -d '[{"labels":{"alertname":"TestAlert","severity":"critical"},"annotations":{"summary":"Проверка доставки"}}]'
# через ~30s (group_wait): журнал Alertmanager → "Notify success"; файл
# /alertmanager/nflog перестаёт быть пустым
```

`nflog` — самый быстрый индикатор: он пуст, пока ни одно уведомление не ушло.

## 3. Горизонтальное масштабирование WS — архитектурный предел

`RoomManager` держит `_members`, `_queues`, `_writers` **в памяти процесса**, а
`back/Dockerfile` запускает Granian с одним worker по умолчанию. Следствия:

- две реплики не увидят соединений друг друга (pub/sub в Valkey есть, но карта
  сокетов — локальная);
- падение процесса обрывает **все** сессии сотрудничества;
- CPU-bound работа (экспорт Excel) блокирует рассылку WS всем.

**Варианты (решение после §1):**
- оставить один процесс осознанно — тогда нужен запас по CPU и метрика
  `ws_connections_active` как индикатор предела;
- вынести карту соединений в Valkey (существенная переделка `RoomManager`);
- sticky sessions на nginx + несколько воркеров (даёт частичный эффект:
  сохраняет соединения при падении части воркеров).

**Статус:** не начато. Нужны числа из §1.

## 4. Метрики, которых пока нет

Добавлено: HTTP (rate/латентность/статусы/размеры), WS (соединения/комнаты/события/медленные
потребители), база данных, очереди выгрузок, импортные фазы, Valkey и runtime.
Остаются сигналы, которые требуют нагрузочного профиля:

- **размер комнаты и задержка writer'а WS** — узкое место при горячей комнате;
- **p95/p99 пользовательских маршрутов и restart-loop** — пороги должны быть
  получены из §1, а не придуманы заранее.

**Статус:** базовый набор сделан (2026-10-29): пул БД, время удержания
соединения, запросы/ошибки/таймауты, очередь и жизненный цикл выгрузок,
импортные фазы, размеры HTTP-тел, Valkey operations и кэш hit/miss уже экспортируются. Дашборд
«Сервис» показывает эти сигналы, а алерты ловят явное исчерпание пула, сбои
выгрузок, блокировку event loop и давление на диск. Нагрузочная калибровка
порогов и production scrape/service discovery остаются в §1 и §6; query-count
и EXPLAIN snapshot закрыты 2026-10-29 и сохранены в
`docs/BACKEND_QUERY_PLANS_2026-10-29.json`.

## 5. Ретенция и объём логов при росте

Сейчас: ротация файла 64 МБ × 5, Loki 7 дней. При 100× нагрузке объём логов
вырастет пропорционально (174 МБ/сутки → ~17 ГБ/сутки).

**Что предусмотреть:**
- сэмплирование `http_request` (не логировать успешные 200 для массовых чтений —
  они уже есть в метриках);
- отсечение `/v1/models` и подобного шума (сейчас это 18% лога — отладчик
  OpenCode ходит не туда; проверить конфиг клиента);
- решение по хранилищу Loki (сейчас filesystem) при переходе на объём.

**Статус:** не начато; триггер — рост дискового объёма или §1.

## 6. Алерты сверх 5xx

Сейчас есть 11 правил: всплеск/накопление 5xx, недоступность скрейпа, медленные
WS-потребители, пул БД, таймауты и deadlock SQL, сбои выгрузок, event loop,
диск, readiness-зависимости и Valkey pub/sub. `infra/prometheus/alert-rules.test.yml`
проверяет, что сравнение пула не смешивает разные экземпляры.

Добавить **после** §1 (нужна базовая линия):
- p95 по маршруту выше baseline × 2 в течение 10 минут;
- `ws_connections_active` растёт, а события не растут (клиенты подключились, но
  данные не идут);
- p95/p99 и saturation для маршрутов, очередей и памяти (§1);
- ошибки миграции/старта: `application_started` чаще 1 раза в 10 минут (цикл
  перезапусков — сейчас в логе было 807 стартов за 33 часа при разработке).

**Статус:** жёсткие отказы и базовые capacity guardrails сделаны 2026-10-29;
пороговые правила по baseline и restart-loop остаются после §1.

## 7. Мелочи, которые всплыли по ходу

- **`port` в `prometheus.yml` захардкожен** (`8000`): Prometheus не подставляет
  переменные compose. При смене `BACKEND_PORT` править файл.
- **`docker compose up` без `--watch` не синхронизирует код** — правки в
  `back/src` не доезжают до контейнера. Для dev всегда `just dev`.
  (Дважды за сессию это привело к «код есть, а в контейнере нет».)
- **`/metrics` не аутентифицирован** — осознанно (скрейп из внутренней сети), но
  при публикации наружу нужен сетевой фильтр.

**Статус:** осознанные ограничения; пересмотреть при deploy в прод.
