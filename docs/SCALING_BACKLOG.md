# Масштабирование и надёжность: что осталось сделать

Рабочий документ. Заведён после настройки наблюдаемости (метрики, дашборды, алерты) —
наблюдаемость **показывает** предел, но не снимает его. Здесь — то, что нужно
сделать, чтобы система выдержала сотни пользователей и постоянное совместное
редактирование.

Порядок = приоритет. Пункты со статусом **НУЖЕН ВНЕШНИЙ РЕСУРС** не сделаны и не
могут быть сделаны без вас (доступ, решение, инфраструктура).

---

## 1. Нагрузочные тесты — их нет вообще

**Почему первым.** Любой порог (latency, число соединений, размер пула БД),
выбранный без базовой линии, — это догадка. Сейчас мы знаем только, что при
3 соединениях p95 ≈ 230 мс. Что будет при 50 — неизвестно.

**Что нужно:**
- сценарий HTTP: чтение грида «Движение» (~94k строк), «Реализация» КППК за месяц,
  экспорт Excel; разными N (1, 10, 50, 100 параллельных).
- сценарий WS: N клиентов в одной комнате, каждый шлёт правки ячейки; замер —
  сколько событий доходит, сколько клиентов отбрасывается по `ws_slow_consumers_total`.
- Инструмент: `locust` (Python, уже есть uv) или `k6`. Для WS `locust` удобнее.
- **Выход:** числа, на которых строятся пороги алертов и принимаются решения по §2–§4.

**Статус:** не начато.

## 2. Доставка алертов по почте — **НУЖЕН ВНЕШНИЙ РЕСУРС**

**Что работает.** Правила (`infra/prometheus/alert-rules.yml`) загружены,
Prometheus отправляет в Alertmanager, Alertmanager группирует; алерты видны в
`http://localhost:9093` и в Prometheus `/alerts`.

**Что не работает.** SMTP. Проверено на практике:

```
Notify attempt failed ... err="establish TLS connection to server:
dial tcp 94.100.180.160:465: connect: connection refused"
```

Порты 25/465/587 закрыты **и с хоста, и изнутри Docker** — проверено `nc -z`
на `smtp.mail.ru`, `smtp.yandex.ru`, `smtp.gmail.com`, `smtp.office365.com`.
IMAP (993) при этом открыт: входящая почта есть, исходящая — нет.

**Что нужно от вас (любое из):**
- корпоративный SMTP-релей, доступный из этой сети (адрес + порт + учётка без
  обязательной MFA для сервисной учётки);
- либо разрешение на исходящий 465/587 к `smtp.mail.ru`;
- либо другой канал доставки (Telegram-бот, webhook в корпоративный мессенджер) —
  тогда `receivers` в `alertmanager.tpl.yml` меняется, правила остаются.

**После получения доступа:** значения уже в `.env` (`ALERT_SMTP_*`),
`SMARTHOST` поменять при необходимости, перезапустить `just logging`, отправить
тестовый алерт:

```bash
curl -X POST http://localhost:9093/api/v2/alerts -H 'Content-Type: application/json' -d '[{"labels":{"alertname":"TestAlert","severity":"critical"},"annotations":{"summary":"Проверка доставки"}}]'
```

**Статус:** НУЖЕН ВНЕШНИЙ РЕСУРС. До появления релея считать «алерты по почте»
**НЕ сделанными**.

## 3. Горизонтальное масштабирование WS — архитектурный предел

`RoomManager` держит `_members`, `_queues`, `_writers` **в памяти процесса**, а
`back/Dockerfile` запускает `uvicorn` **без `--workers`**. Следствия:

- две реплики не увидят соединений друг друга (pub/sub в Valkey есть, но карта
  сокетов — локальная);
- падение процесса обрывает **все** сессии сотрудничества;
- CPU-bound работа (экспорт Excel) блокирует рассылку WS всем.

**Варианты (решение после §1):**
- оставить один процесс осознанно — тогда нужен запас по CPU и метрика
  `ws_connections_active` как индикатор предела;
- вынести карту соединений в Valkey (существенная переделка `RoomManager`);
- sticky sessions на nginx + несколько воркеров (даёт частичный эффект:
  сохраняет соединения при падении части воркеров).

**Статус:** не начато. Нужны числа из §1.

## 4. Метрики, которых пока нет

Добавлено: HTTP (rate/латентность/статусы), WS (соединения/комнаты/события/медленные
потребители). Не хватает того, что покажет предел раньше остального:

- **пул соединений БД** (`db_pool_used` / `db_pool_overflow`) — узкое место
  обнаруживается здесь первым при росте параллельных запросов;
- **время выполнения запросов к БД** (гистограмма по операциям) — чтобы отличить
  «медленный код» от «медленная БД»;
- **очередь экспортных задач** (`export_jobs`/`table_export_jobs`) — длина и
  время ожидания;
- **размер кэша чтения** (`read_cache`) — попадания/промахи.

**Статус:** не начато.

## 5. Ретенция и объём логов при росте

Сейчас: ротация файла 64 МБ × 5, Loki 7 дней. При 100× нагрузке объём логов
вырастет пропорционально (174 МБ/сутки → ~17 ГБ/сутки).

**Что предусмотреть:**
- сэмплирование `http_request` (не логировать успешные 200 для массовых чтений —
  они уже есть в метриках);
- отсечение `/v1/models` и подобного шума (сейчас это 18% лога — отладчик
  OpenCode ходит не туда; проверить конфиг клиента);
- решение по хранилищу Loki (сейчас filesystem) при переходе на объём.

**Статус:** не начато; триггер — рост дискового объёма или §1.

## 6. Алерты сверх 5xx

Сейчас есть 4 правила: всплеск 5xx, накопление 5xx, недоступность скрейпа,
медленные WS-потребители.

Добавить **после** §1 (нужна базовая линия):
- p95 по маршруту выше baseline × 2 в течение 10 минут;
- `ws_connections_active` растёт, а события не растут (клиенты подключились, но
  данные не идут);
- пул БД исчерпан (§4);
- ошибки миграции/старта: `application_started` чаще 1 раза в 10 минут (цикл
  перезапусков — сейчас в логе было 807 стартов за 33 часа при разработке).

**Статус:** не начато.

## 7. Мелочи, которые всплыли по ходу

- **`port` в `prometheus.yml` захардкожен** (`8000`): Prometheus не подставляет
  переменные compose. При смене `BACKEND_PORT` править файл.
- **`docker compose up` без `--watch` не синхронизирует код** — правки в
  `back/src` не доезжают до контейнера. Для dev всегда `just dev`.
  (Дважды за сессию это привело к «код есть, а в контейнере нет».)
- **`/metrics` не аутентифицирован** — осознанно (скрейп из внутренней сети), но
  при публикации наружу нужен сетевой фильтр.

**Статус:** осознанные ограничения; пересмотреть при deploy в прод.
